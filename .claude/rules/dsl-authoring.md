# DSL記述の規約

`src/rules/types.ts` の DSL は全92枚を書き切って収束済み。
**新しいカードを書くためにDSLを拡張する前に、既存のノードで書けないか必ず確認する。**
拡張が必要なら、その理由を `docs/engine-notes.md` に記録する。

## 絶対的な規約

**`as never` / `as any` を書かない。**
過去に「犠牲の残り香」で `countEvent` に存在しない `of` フィールドを渡し、
`as never` で型チェックをすり抜けていた不具合が実在した。
キャストしたくなったら、それはDSLが表現できていないという信号なので、DSL側を直す。

## `countEvent` の落とし穴

**`measure` は必須。** 既定値を置いていないのは、「効果は起きたが数量が0だった」場面で
読みが割れるため（軽減しきったダメージ / ミニオン0体での攻撃指令）。

| 値 | 意味 |
|---|---|
| `'events'` | イベントの発生回数。1イベント = 1 |
| `'units'` | イベントが表す数量の合計（点数 / 体数 / 枚数） |

**`by` は「そのイベントの主体」と照合する**（`GameEvent.player`）。
damageDealt なら与えた側、damageTaken なら受けた側、drawn なら引いた本人、
minionDied なら持ち主。**加害者を引きたいときは `by` ではなく `GameEvent.dealer`。**

## 数え方の落とし穴

**`countTokens` の `kind` は「個数」を数える。**
剣は `maxCopies: 3` なので、剣を3つ持つだけで「武器3種類」が成立してしまう。
「n種類」を判定したいときは**名前で1つずつ検査する**（`objectives.sample.ts` の
「完全武装の証明」を参照）。

**盤面の種族の種類数を数える `Value` は DSL に無い。**
「5種類以上の種族」のような条件は、種族を書き並べる形に読み替える。
そもそもミニオンは人間・天使・死霊・獣の4種類しかない。

## ミニオンの制約

**ミニオンは個体を持たない。** 盤面上の状態は `MinionPool`（種族 → 体数）だけで、
個体ID・体力・攻撃力を持たない。**1点のダメージにつき1体が消える。**

- 「ミニオン1体を対象に取る」効果は作れない
- 「このミニオンに+1/+1」「このミニオンは対象に取られない」は作れない
- 「この種族は対象に取られない」は作れる

## 詠唱（chant）

- `chant` キーワードを持つカードは**プレイ時に詠唱カウンターが1つ乗った状態で始まる**。
  「プレイしたとき詠唱カウンターをさらにn個置く」という文面はその上に乗る
- **スタック上に生成された「効果」に詠唱カウンターは乗らない。**
  「海の神の*カード*が置かれるたび」の対象はカードのみ。効果を数えると自己加速ループが生まれる。
  `StackFilter.kind: 'card'` で絞る

## 常在（static）

テキスト表記は「常在」1つだが、実装は3つに分解される（設計書 §4）。
**効果が `whileOnStack` の付与だけで構成されるアクション項目は、解決時ではなく配置時に付与される**
（解決時に実行するとその瞬間に消えるため）。

## handler に逃がす基準

盤面構造そのものを組み替えるもの（デッキ分割、スタック分割、山札の合流）は
DSLで書かず handler に逃がす（設計書 §7）。創造の神は「handlerの神」として
handler比率が高いことを許容し、その代わりカード枚数を少数精鋭にする。

未登録の handler は `NotImplementedError` になる。これは設計どおりで、穴ではない。

## 勝利条件（`ObjectiveDef`）

- **先行度は全神を通して一意。** 重複は `setupObjectives` が弾き、
  `objectives.data.test.ts` が総当たりで検証している
- `when` が `TriggerEvent` なら通常の誘発と同じ経路、`{ on: 'continuous' }` なら状況起因判定
- **`{ on: 'continuous' }` は既定で1ゲームに1回だけ発火する。** 繰り返したいなら `limit` を明示する
- `effect` を省略すると「その条件の持ち主が勝利する」の意味になる
- 状況起因の判定は**安全地点でのみ**行う。効果の途中で一瞬成立しても勝利しない
- データ化で判断した点は各条件の `note` に書く
