# 特殊勝利条件を追加する

## 1. 一次資料

企画書「基本システム」シート C55〜C111 に、神ごとの勝利条件案が並んでいる。
現在データ化されているのは**先行度の仮配分が振られている各神3つずつ、計12件**。

<https://docs.google.com/spreadsheets/d/1wsqflPdIjVbylahHXCFgm3aokhKRDwK4frGZlW5ItDI/edit>

見送った候補と、その理由（DSLで表現できない / 企画側が未決 / 先行度の枠が埋まった）は
`docs/engine-notes.md` の「見送った候補」に列挙してある。**同じ候補を再検討する前にそこを読む。**

## 2. 先行度を決める

**先行度は全神を通して一意。** 重複していると `setupObjectives` が `RuleError` を投げ、
`objectives.data.test.ts` が総当たりで検証して落とす。

現在の割り当て（0〜15のうち、創造の 0/11/13/14 を除いた12個を使用中）:

| 神 | 先行度 |
|---|---|
| 大地 | 1, 3, 6 |
| 生命 | 2, 8, 12 |
| 空 | 4, 7, 9 |
| 海 | 5, 10, 15 |
| 創造 | 0, 11, 13, 14（枠のみ。調整中） |

**空き番号を使うか、既存の条件と入れ替える。** 1に近いほど先攻。

`initiative: 'special'`（創造の特殊枠）は数値と比較できないため**最後尾扱い**の暫定処理。
企画側で数値が決まればこの分岐は消える。

## 3. `when` を選ぶ

判定経路は2つしかない。

| `when` | 経路 |
|---|---|
| `TriggerEvent` | 通常の誘発とまったく同じ（`events.ts` の `gatherSources` が第5の発生源として拾う） |
| `{ on: 'continuous' }` | 状況起因判定（`checkObjectives` が安全地点ごとに走査する） |

**`{ on: 'continuous' }` の落とし穴:**

- **既定で1ゲームに1回だけ発火する**（`CONTINUOUS_DEFAULT_LIMIT`）。
  成立している間ずっと真なので、制限が無いと判定のたびに発火する。
  繰り返したい条件は `limit` を明示する
- **判定は安全地点でのみ行われる。** ひとつの効果の途中で一瞬だけ条件が成立しても勝利しない。
  「ライフがちょうど35なら勝利」は、5点回復してから100点回復する効果では成立しない。
  これは意図した仕様（MTGの状況起因処理と同じ）

`cond` は誘発型では `TriggerEvent.cond` に合流する（両方あれば `and`）。
`effect` を省略すると「その条件の持ち主が勝利する」の意味になる。
`passive` は公開されている間だけ効く `ContinuousMod`（`gatherMods` の⑤番目の発生源）。

## 4. 書けるかを先に確かめる

DSLで表現できない条件がある。過去に見送った理由:

- **カードの由来ゾーンを追跡する仕組みが無い**（海「4つの場所からカードを手札に加えた」）
- **デッキ構築制約を表現する手段が無い**（海「40枚デッキで」）
- **引き切りペナルティは即敗北ではない**ので「敗北の代わりに勝利」が噛み合わない
- **盤面の種族の種類数を数える `Value` が無い**（生命「5種類以上の種族」→
  「4種類それぞれn体以上」に読み替えた）

書けないと判断したら、**DSLを拡張する前に**その旨と拡張案を報告して止まる。

## 5. 検証する

```
npm run typecheck
npm test
npm run sweep
```

`objectives.test.ts`（エンジン20件）と `objectives.data.test.ts`（データ27件）が
勝利条件を担保している。**新しい条件を足したら、そこにテストも足す。**
最低限、達成できる盤面と達成できない盤面の2本。

## 6. 記録する

**データ化で下した判断は必ず条件の `note` に書く。** 既存の条件がすべてそうなっている。
企画側の判断を仰いだ点や、企画書の記述から読み替えた点は
`docs/engine-notes.md` にも追記する。

数値が仮のもの（生命「4種類それぞれ5体以上」の5体など）は、**仮であることを `note` に明記する。**
