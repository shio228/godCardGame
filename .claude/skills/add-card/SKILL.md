# カードを追加する

## 1. 一次資料を読む

カードの一次資料は**各神の設定シート**（大地の神設定 / 海の神設定 / 空の神設定 /
生命の神設定 / 創造の神設定）。**「カード置き場」シートは古いので参照しない。**

企画書 <https://docs.google.com/spreadsheets/d/1wsqflPdIjVbylahHXCFgm3aokhKRDwK4frGZlW5ItDI/edit>

色分けを必ず確認する。**赤字・青字は未合意の草案**なので、確定仕様として実装しない。
黒太字が合意済み、黒細字が仮採用。判断が要る点が残っていたら、実装せずに何を決める
必要があるかを報告する。

## 2. 既存の似たカードを探す

書き始める前に `src/rules/cards.sample.ts` から**同じ挙動をする既存カードを探して真似る。**
92枚が既にあるので、たいていの効果には前例がある。前例が無い書き方をしている自覚が
出たら、それは設計判断が要るという信号。

`docs/rule-engine-design.md` の §3（戦技・攻撃指令・防御指令・レゾナンスは同じ仕組み）と
§6（DSL拡張の経緯）に、どの効果がどのノードに落ちるかが書かれている。

## 3. 書く

`src/rules/dsl-authoring.md` の規約に従う。特に:

- **`as never` / `as any` を使わない。** 使いたくなったらDSL側を直す
- **`countEvent` の `measure` は必ず明示する**（`'events'` か `'units'` か）
- 「n種類」の判定は `countTokens` の `kind` ではなく**名前で1つずつ検査する**
- ミニオンは種族と数だけ。個体を対象に取る効果は書けない
- `chant` を持つカードは詠唱カウンター1から始まる

**DSLを拡張しないこと。** どうしても既存ノードで書けない場合は、拡張案と理由を提示して
止まる。DSLの変更は92枚すべてに影響する。

## 4. 検証する

```
npm run typecheck
npm test
npm run sweep
```

**3つとも通すこと。** sweep は成功数だけでなく**エラーの内訳を追加前と比較する。**

sweep で新しいカードが落ちた場合、原因は3種類ある。取り違えないこと:

| エラー | 意味 | 対応 |
|---|---|---|
| `NotImplementedError: handler "..."` | handler未登録 | 設計どおり。handlerを書くか、そのまま残す |
| `RuleError: プレイ条件を満たしていない` | sweepの空盤面が条件を満たしていないだけ | **正常。** 直さない |
| `RuleError: このフェイズにはプレイできない` | 同上（騙し討ちなど） | **正常。** 直さない |
| 上記以外の例外 | 本当のバグ | 直す |

追加前の基準値は `docs/roadmap.md` の「現在地」にある。

## 5. 記録する

DSL化にあたって解釈の判断を下した点は、**カードのコメントに残す**
（`objectives.sample.ts` の `note` と同じ流儀）。
企画側の判断を仰いだ点や、企画書の記述と実装がずれた点は
`docs/engine-notes.md` に追記する。
