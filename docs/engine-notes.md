# 解決エンジン実装メモ（v2）

`src/engine/` に `resolve(effect, ctx)` のインタプリタと、それを1試合分回す
ターン進行・天候・自動対戦を実装した。
設計書 `rule-engine-design.md` の確定事項をそのままコードに落としたもので、
DSL 側（`src/rules/types.ts`）への変更は `countEvent.measure` の追加1件のみ
（`state.ts` の `Bound` に `weather` 枝、`GameState` に `winReason` を足したのは
エンジン内部の表現なので DSL の変更ではない）。

```
npm run typecheck   # tsc --noEmit（strict + exactOptionalPropertyTypes）
npm test            # ゴールデンテスト 115件
npm run sweep       # 全92枚を空盤面で走らせ、落ちるカードを一覧にする煙テスト（88/92）
npm run simulate    # 自動対戦。神別勝率・決着サイクル・勝因・先攻後攻差を出す
npm run replay      # 1試合を記録して再生する
npm run dashboard   # 上記をまとめた HTML（テスト・煙テスト・自動対戦・リプレイ）
npm run deck        # 手組みデッキ（decks/*.txt）の検証と要約
npm run play        # 対話プレイ
npm run builder     # デッキビルダー（ブラウザで組む1枚のHTML）
```

## 実装で決めたこと

### 1. 選択は async/await + `Chooser`

`resolve` は `Promise` を返し、選択は `await ctx.engine.chooser.select(...)` で待つ。
テストは `ScriptedChooser`（応答を配列で与える）、ランダム対戦は `AutoChooser`、
UI は「クリックで解決される Promise」を返す実装を差し込む。

代償として**解決の途中状態はシリアライズできない**。リプレイや巻き戻しを
解決の粒度で行いたくなったら、ジェネレータ（`yield` で中断）への移行が必要になる。
いまは `snapshot()` を効果の境界で取る運用で足りる想定。

### 2. 状態はミュータブル + `structuredClone` のスナップショット

`GameState` を直接書き換える。テスト・巻き戻しは `snapshot()` / `restore()`。

### 3. 未対応ノードは必ず例外

`NotImplementedError` / `RuleError` / `BindingError` / `LoopError` を用意し、
黙って何もしない経路を作っていない。束縛名の解決失敗も 0 に落とさず例外にする。

### 4. 置換効果は必ず1本の経路を通る

- ライフの増減はすべて `changeLife()`（根性 = `lethalReplacement` がここで働く）
- ドローはすべて `drawCards()`（`drawDelta` がここで働く）
- ダメージはすべて `dealDamage()`

直接 `p.life -= x` や `hand.push(deck.pop())` を書ける場所をエンジン内に作っていない。

### 5. 誘発の順序（暫定規約）

設計書 §10 の宿題に対する現在の実装:

1. イベントは即座に誘発を実行せず `engine.pending` に積む
2. `drainTriggers` が **先攻プレイヤー → 後攻プレイヤー** の順に流す
3. 同一プレイヤー内に複数あるときは `chooser.order` で本人に順序を選ばせる
4. 処理中に積まれた誘発は同じループで続けて処理する

### 6. 無限ループ検出

`engine.budget`（既定10000ステップ）を超えたら `LoopError`。
加えて `engine.resolving` で「解決中の項目を再び解決しない」ようにしている
（これがないとスプリットディメンションの `resolveStack {t:'all'}` が自分自身を
巻き込んで無限再帰する）。

## 企画側で確定した仕様（2026-08-30）

1. **詠唱カウンターの初期値は1**。「プレイしたとき詠唱カウンターを**さらに**5つ置く」
   という文面どおり、`chant` キーワードを持つカードはプレイ時に1つ乗った状態で始まる。
   アンプリファイバブルシールドの軽減量は 6 から始まる。
2. **ミニオンは1点=1体で消える**。体力を持たない仕様なので、割り振られたダメージ1点につき
   1体が失われる。防御指令・天使の吸収量がこれで決まる。
3. **常在を持つ NamedAction は「乗せた時点」から働く**。防御指令の効果は
   `grantContinuous(duration:'whileOnStack')` なので、解決時に実行したのでは
   その瞬間に消えてしまう。効果が whileOnStack の付与だけで構成されるアクション項目に限り、
   配置時に付与を実行している。
4. **引き切りペナルティで敗北したらそこでゲームが終わる**。不足2枚なら
   「30点のダメージを受ける」が2つスタックに積まれるが、1つ目でライフが0になった時点で
   勝敗が決まり、2つ目は解決されない。
5. **`countEvent` は `measure` で数え方を必ず明示する**（下記）。

## `countEvent.measure`（必須フィールド）

「回数」と「数量」は、**効果は起きたが数量が0だった**場面で結果が割れる
（軽減しきったダメージ / ミニオン0体での攻撃指令）。既定値を置くとどちらの読みか
分からなくなるので、`measure` を必須にして毎回書かせる。

| 値 | 意味 | 例 |
|---|---|---|
| `'events'` | イベントの発生回数。1イベント = 1 | 「天候が5回変わったなら」 |
| `'units'` | イベントが表す数量の合計（点数 / 体数 / 枚数） | 「死亡したミニオンに等しい数」「ダメージを受けていないなら」 |

`GameEvent.units` がその数量を持つ。damageDealt の units は
**「与えたダメージ」（修正込み・軽減前）**、damageTaken の units は
**「実際に通ったダメージ」** — 設計書 §5 の用語に合わせている。
`granularity: 'perUnit'` の反復数も同じ `units` を見る。

現時点のカード92枚での使い分け（`countEvent` は7箇所）:

| カード | イベント | measure |
|---|---|---|
| リアクティブアクアスフィア | damageDealt | `units` |
| 栄光の凱旋 | damageDealt | `units` |
| フローレスフェザー | damageTaken | `units` |
| 犠牲の残り香 | minionDied | `units` |
| 最期の献身 | minionDied | `units` |
| 明鏡止水 | weatherChanged | `events` |
| セレスティアル・ディザスター | weatherChanged | `events` |

`drawn` を `countEvent` で数えるカードはまだ1枚もない。

**`countEvent.by` は「そのイベントの主体」**と照合する（`GameEvent.player`）。
damageDealt なら与えた側、damageTaken なら受けた側、drawn なら引いた本人、
minionDied なら持ち主。加害者を引きたいときのために `GameEvent.dealer` を別に持っている。

### この作業で見つかったデータ側の不具合

**犠牲の残り香**の `countEvent` が `of: { t: 'self' }` を渡していた。
`countEvent` に `of` というフィールドは無く、`as never` でキャストして
型チェックをすり抜けていた（`countSpeciesKinds` からのコピーと思われる）。
`by: { t: 'self' }` に直してキャストを外した。
**`as never` / `as any` はDSLの穴を隠すので、今後は入れない。**

## 特殊勝利条件（`objectives.ts`）

企画書「基本システム / 基本ルール」のルールをそのまま実装した。

### 公開と先攻決定

- `setupObjectives(engine, player, ids)` … 採用した条件を伏せてセットする。
  **3つ未満・他の神の条件・先行度の重複**をここで弾く
  （「先行度は同じ数字を持たない」を、先攻決定が引き分けになる前に検出する）。
- `revealPhase(engine)` … ①サイクル開始フェイズの公開。`startCycle` の先頭で呼ぶ。
  **両者の選択を先に集めてからまとめて公開する**。1つずつ公開すると後に選ぶ側が
  相手の先行度を見てから決められてしまい、「見せあって決める」というルールにならない。
- `determineFirst(engine)` … 両者が**最後に公開した**条件の先行度を比べ、
  1に近い方を先攻にする。公開し尽くしたサイクル3以降は公開が起きないので、
  「最後の数値で固定」は特別な分岐なしにそのまま成り立つ。
- 公開は `objectiveRevealed` イベントとして誘発できる（`GameEvent.objectiveId` に id が載る）。
  カード効果 `revealObjective` もこの経路を通るが、**先攻は決め直さない**
  （先攻が動くのはサイクル開始の公開だけ）。

### 判定は2経路

`ObjectiveDef.when` の形で分かれる。

| `when` | 経路 | 実装 |
|---|---|---|
| `TriggerEvent` | 通常の誘発とまったく同じ | `events.ts` の `gatherSources` が第5の発生源として拾う |
| `{ on: 'continuous' }` | 状況起因判定 | `checkObjectives` が安全地点ごとに走査する |

`ObjectiveDef.cond` は誘発型では `TriggerEvent.cond` に合流させる（両方あれば `and`）。
`effect` を省略した条件は **「その条件の持ち主が勝利する」** の意味になる。
`passive` は公開されている間だけ効く `ContinuousMod` で、`gatherMods` の⑤番目の発生源。

### 判定地点は `drainTriggers` の1か所だけ

`checkObjectives` の呼び出しは `drainTriggers` の先頭にしか置いていない。
プレイ後・スタック項目の解決後・各フェイズはすべて `drainTriggers` を通るので、
呼び忘れで判定が漏れる場所を作らずに済む。`drainTriggers` は
「pending が空でも1周は回る」形に変えてある。

### ここで決めた仕様（4点とも企画側の承認済み・2026-08-31）

1. **状況起因の判定は安全地点でのみ行う**（MTGの状況起因処理と同じ）。
   ひとつの効果の途中で一瞬だけ条件が成立しても勝利しない。
   例: 「ライフがちょうど35なら勝利」は、5点回復してから100点回復する効果では成立しない。
2. **`when: {on:'continuous'}` の条件は既定で1ゲームに1回だけ発火する**
   （`CONTINUOUS_DEFAULT_LIMIT`）。成立している間ずっと真なので、
   制限がないと判定のたびに発火してしまう。繰り返したい条件は `limit` を明示する。
   → このために `ObjectiveDef.limit?: Limit` を1フィールドだけ追加した（DSLの変更はこれだけ）。
   代案（`limit` を必須にする／条件が偽に戻ったら枠を戻すエッジ検出）は検討のうえ不採用。
3. **`initiative: 'special'`（創造の特殊枠）は最後尾扱い**。数値と比較できないため。
   'special' 同士なら前サイクルの先攻を維持する。企画側で数値が決まればこの分岐は消える。
   創造の神は調整中のため、当面この扱いのままにする。
4. 数値の先行度が両者で並んだら `RuleError`。「先行度は一意」というルールをデータの誤りとして扱う。

### 条件データ（`src/rules/objectives.sample.ts`）

企画書「基本システム」C55〜C111 の一覧から、**先行度の仮配分が振られている各神3つずつ**を
データ化した（計12件、`samplePool.objectives`）。

| 神 | 先行度 | 条件 |
|---|---|---|
| 大地 | 1 | 十連撃の誓約 — 10回目のダメージを与えたなら勝利 |
| 大地 | 3 | 完全武装の証明 — 武器3種・防具2種をコントロールし打撃でダメージを与えたなら勝利 |
| 大地 | 6 | 一撃必殺 — 1度の攻撃で8点のダメージを与えたなら勝利 |
| 生命 | 2 | 生命の氾濫 — ターン開始時にライフ99以上なら勝利 |
| 生命 | 8 | 生死の振幅 — お互いのライフが50回以上変動したら勝利 |
| 生命 | 12 | 万象の軍勢 — 4種類それぞれ5体以上コントロールしているなら勝利 |
| 空 | 4 | 無限連鎖 — 自分の効果が一度に15個スタックに乗ったら勝利 |
| 空 | 7 | 天象二十変 — 累計20回天候が変わったら勝利 |
| 空 | 9 | 連鎖する空 — 自分の項目がスタック上で7つ連続したら勝利 |
| 海 | 5 | 詠唱の極致 — スタック上の詠唱合計が30以上で勝利 |
| 海 | 10 | 叡智の飽和 — ターン終了時に手札ちょうど15枚で勝利 |
| 海 | 15 | 完全なる水位 — ターン開始時にライフちょうど35で勝利 |

先行度は 0〜15 のうち創造の 0/11/13/14 を除いた12個で、**全神を通して一意**
（`objectives.data.test.ts` が総当たりで検証している）。

データ化で判断した点は各条件の `note` に書いた。企画側の判断が入ったのは次の3つ（すべて確定）。

1. **一撃必殺の「8点」は軽減後（実際に通ったダメージ）で判定する。**
   暗黙束縛 `amount` がその値なのでそのまま使っている。設計書§5の用語では「与えたダメージ」は
   軽減前だが、ここは「相手が軽減で防げる＝対策の余地がある」側を採った。
2. **十連撃の「10回」は0点だったダメージも1回と数える。** `measure:'events'` の性質そのまま。
   企画書には「0ダメでも数えるから納得いかないかも」というコメントがあったが、これでよいと確定。
3. **生命の「5種類以上の種族」は「4種類それぞれ5体以上」に読み替えた**（企画書のアレンジ案）。
   ミニオンは人間・天使・死霊・獣の4種類しかなく原文のままでは達成不可能なため。
   **5体はテスト段階の仮の数値**で、変わる前提。

もうひとつ、企画側の判断ではないがデータ化で決めた点として、
**「武器3種類・防具2種類」は名前で1つずつ検査している**。`countTokens` の `kind` は個数を数えるので、
剣（maxCopies:3）を3つ持つと「武器3種類」になってしまうため。装備の種類が増えたらここも直す。
同じ理由で「4種類それぞれ5体以上」も種族を書き並べている
（盤面の種族種類数を数える `Value` が DSL に無い）。

### 見送った候補

- 海「40枚デッキで引き切ったら敗北の代わりに勝利」— 引き切りペナルティは即敗北ではなく
  「30点ダメージをスタックに追加」なので噛み合わない。デッキ構築制約の表現も無い。
- 海「天候が雨の状態が2サイクル継続」— 企画書に「どこで判定するか」と未決の書き込みあり。
- 海「4つの場所からカードを手札に加えた」— カードの由来ゾーンを追跡する仕組みが無い。
- 空「手札7枚で始まったターンに手札0でカウンター、3以上で勝利」— 企画書に「不可能っぽい」とある。
- 生命「このターン終了時にミニオン合計数が40（仮）以上なら」— 書けるが先行度の枠が埋まった。
- 大地「このターン発生したダメージを全て0まで軽減できたら勝利」— 書けるが先行度の枠が埋まった。
  「一度もダメージを受けていない」場合も成立してしまう点も要判断。
- 数値未定のもの（生命「ミニオンをn体以上」×2、海「除外枚数n以上」）。

### まだ無いもの

- 創造の神の特殊な公開ルール（企画側で調整中）。
  （「複数選んで最も先行度の低いものだけ公開」「この勝利条件は公開できない」
  「先行度0＝他を選べず必ず先攻・初期手札5枚」）。
  現状の穴: `initiative:'special'` の条件も `revealPhase` の選択肢に普通に並ぶ。
  本来はサイクル開始では選べず、条件が成立したときに自動で公開されるべきもの。
  先行度0 の条件は `setupObjectives` に `min: 1` を渡さないと「3つ未満」で弾かれる。
  伏せる／指摘する系の効果も DSL に無い。
- 勝利条件を**伏せ直す**効果（企画書に言及あり）。

## ターン進行（2026-09-02）

`flow.ts` に企画書「基本ルール」のフェイズをそのまま関数として置き、
`runGame` が1試合を回す。1サイクル = 1ターンで、両者が同じスタックに交互に積む。

```
startGame → [ startCycle → drawPhase → stackPhase → orderPhase → resolvePhase → endTurn → endCycle ] * n
```

| ファイル | 追加したもの |
|---|---|
| `flow.ts` | `startGame` / `drawPhase` / `stackPhase` / `orderPhase` / `runGame` / `surrender` / `playChoices` |
| `weather.ts` | 天候定義テーブルと能動効果（新規） |
| `handlers.ts` | 標準 handler 3件（新規） |
| `decks.sample.ts` | 検証用のサンプルデッキ（新規・`src/rules/`） |
| `tools/simulate.ts` | 自動対戦ハーネス（新規） |

### ここで決めたこと

1. **プレイできるタイミングの既定はスタックフェイズ。**
   `PlayRule.timing` を省略したカードはスタックフェイズにしかプレイできない。
   企画書の「瞬発はスタックフェイズにのみ使用できる」はこの既定から自動的に出る。
   **例外は騙し討ち**で、瞬発を持ちながら `timing:['orderPhase']` を明示している
   （テキストも「順番確定フェイズの開始時にプレイしてもよい」）。
   **カード側の明示がルールの既定に優先する**という扱いにした。

2. **瞬発はプレイした直後に解決してスタックから降ろす。**
   誘発で打ち消された・場所を移された場合は解決しない（`isOnStack` で確認する）。
   sweep は「まだスタックに残っている項目だけ手で `onResolve` を叩く」ようにした。

3. **`resolving`（解決しようとするたび）の誘発は、解決の中身より先に処理する。**
   FAQ の確定事項「スタック解決始め（炎天ダメージ判定）→ 解決中 → 解決終わり」に合わせた。
   その誘発で項目が打ち消されたなら解決しない。

4. **追加コストは「払えないと確実に分かる形」だけ事前に弾く**（`canPayCost`）。
   手札が足りない捨て札と、いないミニオンの生贄の2つ。判定できない形は払えるものとして扱う。
   これが無いと「手札0枚で『1枚捨てる』を払ったことにして代替プレイを無限に繰り返す」穴ができる。

5. **プレイするカードは追加コストより先に手札から取り除く。**
   後にすると「手札を1枚捨てる」コストで自分自身を捨てられ、墓地とスタックに同じカードが並ぶ。

6. **`runGame` は決着しなければ例外**（既定20サイクル）。黙って引き分けにしない。
   30枚デッキなら4サイクル目で引き切り、5サイクル目のドローで引き切りペナルティが出るので、
   放っておいても決着するのが設計上の想定。

7. **`GameState.winReason` を追加した。** 勝敗を決める唯一の入口 `setWinner(state, winner, reason)` を
   `state.ts` に置き、ライフ0 / 降伏 / 効果 / 勝利条件名を記録する。
   自動対戦の「特殊勝利ごとの達成率」がこれで出せる。すでに決まっている勝敗は上書きしない
   （吹雪の同時死亡で「先に死んだ方が負け」が成り立つのはこの性質）。

## 天候の能動効果（2026-09-02）

企画書「基本システム」の天候表をそのまま `WEATHER_DEFS`（`weather.ts`）に写した。

| 天候 | 効果 | 実装 |
|---|---|---|
| 晴 | 攻撃が必ず当たる | `noEvasion`（ダメージ段9） |
| 炎天 | 晴に加え、プレイ時と解決しようとする時にコントローラーへ1点 | `GrantedTrigger`（played / resolving） |
| 雨・豪雨 | サイクルボーナス無視 | `noCycleBonus`（ダメージ段2） |
| 豪雨 | プレイごとに手札1枚捨て | `GrantedTrigger`（played） |
| 吹雪 | ターン終了時に両者5点 | `GrantedTrigger`（turnEnd） |
| 雷雲 | 各スタックのカード1枚をランダムに無効化 | `applyWeatherNegation`（順番確定フェイズの最後） |
| 終末 | ターン開始時に山札を1つ選び上から5枚除外 | `GrantedTrigger`（cycleStart） |

### ここで決めたこと

1. **注入ではなく収集にした。** roadmap では「テーブルから state に `ContinuousMod` /
   `GrantedTrigger` を注入する」と書いていたが、天候が変わるたびに古い分を回収する必要があり、
   取りこぼすと幽霊の天候効果が残る。`gatherSources` と同じ「いま有効なものをその都度集める」
   形にした（`weatherTriggerSources` が誘発の第6の発生源）。

2. **天候の誘発はプレイヤーごとに1組ずつ作り、`weatherImmune` はそこで落とす。**
   炎天のダメージも豪雨の手札破棄もこの1か所で免除されるので、効果ごとに免疫判定を書かずに済む。
   吹雪が「先攻 → 後攻」の順に処理されるのもこの形の副産物で、
   企画書の「吹雪による同時死亡の際は先行度が早い方が敗北」がそのまま成立する。

3. **天候ダメージは「与えた側」を持たない**（`dealerOf`）。
   `tags:['weather']` のダメージは `damageDelta direction:'dealt'` も `damageFlagGrant` も通さず、
   `damageDealt` イベントにも主体を載せない。
   これが無いと炎天や吹雪のダメージが**受けた本人が与えたダメージ**として扱われ、
   大地の「攻勢」が乗り、「10回目のダメージを与えたなら勝利」まで進んでしまう。
   天候ダメージへの修正は受ける側で書く — 気炎万丈の「炎天のダメージにダメージボーナスが
   付与される」が `direction:'taken'` で書かれているのがその形。

4. **天候ダメージは軽減も回避もされない**（`WEATHER_DAMAGE_FLAGS`）。
   企画書「基本ルール」の「天候から与えられるダメージはそれ用のカードがない限り
   軽減できず、回避できない」。`damagePrevention` と `weatherImmune` は通る（自在の神翼）。
   装甲は減算のままにしてある（`DamageFlags` が軽減と装甲を別扱いにしているため）。

5. **炎天の解決時ダメージは `resolved` ではなく `resolving`。** FAQ の
   「炎天・燃え盛るのダメージはスタックを解決しようとしたときに飛ばす」に従った。

6. **雷雲の無効化は `weatherNegate` イベントを出してから打ち消す。**
   置換効果（雷光顕現の「代わりにミニオンを生贄」／レイジングスカイの「対象外になる」）が
   そこに割り込む。無効化そのものは `counterStack` を通す（墓地送りと `countered` イベントを共有）。

## `replaceEvent`（汎用置換）

雷雲の実装に必要になったので、優先度4から前倒しで実装した（`continuous.ts`）。

- `tryReplaceEvent(ctx, ev)` が `true` を返したら**元の処理は行わない**
- `with` を省略すると単に打ち消す / `optional` なら「代わりに〜してもよい」
- **実際に置換を通している経路は `REPLACEABLE_EVENTS` に列挙**してあり、
  そこに無いイベントの置換が付与されたら `NotImplementedError` を投げる
  （置換が素通りする＝黙って無視する経路を作らないため）。現状は `weatherNegate` のみ。
  現データの `replaceEvent` は雷光顕現とレイジングスカイの2枚で、どちらも `weatherNegate`

## 手札上限 / 代替プレイ / キーワード付与

- **`handLimit`**: 終了フェイズに上限（既定10、企画書の「手札上限10 ←持ち越し最大数」）を
  超えた分を捨てる。捨てるのは `discard` 効果を通す。`amount:'none'` で無制限（叡智保管庫）。
  複数の `handLimit` があるときは後から掛かったものが勝つ
- **`alternativePlay`**: 「1枚プレイする代わり」なので、スタックフェイズの選択肢
  （`playChoices`）に通常のカードと並べる。コストを払えないものは選択肢に出ない
- **`grantKeyword`**: `gatherMods` に**手札のカード（`active:'inHand'`）を第6の発生源として追加**した
  （それまで `inHand` の継続的効果はどこからも収集されていなかった）。
  唯一の使用例スカイエンハンスが「**このカードを**瞬発を持つかのようにプレイしてもよい」なので、
  **手札のカード由来の付与はそのカード自身にだけ効く**と解釈している。
  発生源がカードでない付与は対象を特定する手段が DSL に無いため `NotImplementedError`

## 付与された効果と snapshot

`grantContinuous` / `grantTrigger` は、付与した時点の**発生源の snapshot を写し取る**ようにした。

付与された効果は発生源より長く生きうる（瞬発カードが解決してスタックから降りても
`thisCycle` の効果は残る）ため、snapshot を項目に置いたままだと参照できなくなる。
ブレイジングラッシュの「このサイクル終了時に**それらのカード**を墓地に置く」が
`BindingError` で落ちていたのがこれ。

同じ理由で、`damage.ts` の種族フィルタ（`damageDelta.species` など）は
**ダメージ側の ctx ではなく mod 側の ctx（`modCtx`）で評価する**ように直した。
威光の紋章の「選んだ種族の攻撃指令に＋3」がダメージ計算のたびに束縛を見失っていた。

## 標準 handler（`handlers.ts`）

`createEngine` の既定レジストリを `coreHandlers()` にした。

| id | カード | 実装 |
|---|---|---|
| `sea/splitDeck` | 並列思考 | デッキを選んでシャッフルし n 等分。以降 `drawCards` が引く山を選ばせる |
| `creation/stackSplit` | スタック分割 | その項目を先頭にした新しいスタックを作る。`resolveFirst` なら `stacks` の先頭に置く |
| `creation/mergeDecks` | ケイオス・フォーチュン | 全デッキを1つに統合し、**両者の `zones.deck[0]` が同じ配列を指す**ようにする |

これに伴うエンジン側の変更:

- `resolvePhase` は**全てのスタック**を先頭から順に空にし、終わったら1本に戻す
- `play` はスタックが複数あるとき乗せる先を選ばせる
- `drawCards` は山が複数あるとき引く山を選ばせる（並列思考の「任意のあなたのデッキを選べる」）

共通デッキを「同じ配列への参照」で表しているのは、`snapshot()` の `structuredClone` が
同一参照を同一参照のまま複製するため。どちらが引いても同じ山が減るのが「共通」の意味。

## 記録と再生（2026-09-02）

`replay.ts` に「1試合を完全に再現できる記録」と、その再生を実装した。
自動対戦で落ちた試合を手元で1手ずつ追うためのもの。

### 何を記録すれば再現できるか

エンジンの乱数は `GameState.rng`（シード固定のLCG）**だけ**で、
`Math.random` も時刻も使っていない。したがって

- **盤面の乱数**（シャッフル・ランダム選択・雷雲の無効化先）はシードで決まる
- **足りないのはプレイヤーの選択**。`RandomChooser` ならシードで決まるが、
  人間やUIが打った試合はそうならない

そこで **`Chooser` の応答を1件ずつ記録し、再生時はそれを読み上げる**形にした
（`RecordingChooser` / `ReplayChooser`）。打ち手の種類（ランダム / AI / 人間 / UI）を
問わず同じ仕組みで再生できる。

### ここで決めたこと

1. **選択は値ではなく「選択肢の番号」で記録する。** カードやスタック項目は
   実行のたびに別のオブジェクトになるので、値では突き合わせられない。
   同じ値が複数並ぶ選択肢でも番号が重ならないようにしてある。
2. **番号と一緒にラベルも記録し、再生時に毎回突き合わせる。**
   食い違ったら `ReplayError`。つまり**エンジンの挙動を変えると古い記録の再生が失敗する**。
   これは仕様で、退行の検出に使う。
3. **例外で終わった試合も記録を返す。** 落ちた試合を再現できることがこの仕組みの主目的なので、
   `recordGame` は中で例外を捕まえて `result.error` に残す。再生も同じ例外で終わることを確認する。
4. **一致判定は結果だけでなくログ全行を見る。** 勝者・サイクル・勝因・例外に加えて
   ログの行数と本文を先頭から比較し、最初に食い違った行を報告する。
5. **1試合のシードは (基準シード, 神の組み合わせ, 何戦目) のハッシュ**（`tools/simulate.ts` の `gameSeed`）。
   `--games` を変えても同じ試合が同じシードで再現できる。連番にすると
   試合数を変えたとたんに対応が崩れる。

### 全アクションのログ

`LogEntry` に `kind` / `cycle` / `phase` / `player` を足し、行動として意味のある行に
`logAction` で `kind` を付けた（`phase` / `play` / `pass` / `draw` / `reveal` /
`resolve` / `trigger` / `weather` / `win`）。

- `kind` のある行だけを拾えば「誰が何をしたか」の棋譜になる（`--log actions`）
- `kind` の無い行は効果の内部の記録（ダメージ・公開など）。`--log all` で出る
- どの行にも記録時のサイクルとフェイズが入っているので、時系列で読める

1. **同神対決はルール上起こらない。** したがって「先行度が両者で並ぶ」のはデータの誤りであり、

## 目的志向AI（2026-09-02）

勝利条件は `ObjectiveDef.cond` という**データ**なので、`evalValue` / `evalCondition` を
そのまま使って「いまどこまで進んでいるか」を数字にできる（`progress.ts`）。
AI 側に「詠唱を貯めろ」「ミニオンを並べろ」といった知識は1つも書いていない。

### 達成度（`conditionProgress`）

| 形 | 達成度 |
|---|---|
| `cmp >=` | `a / b` を0〜1に切り詰める（「あと何点で届くか」） |
| `cmp ==` | 差の小ささ（完全なる水位のライフちょうど35） |
| `and` | 子の**平均**。min にすると最悪の1つが動くまで進捗0のままでAIの手掛かりにならない |
| `or` | 子の最大 |
| その他 | 条件を評価して 1 / 0 |

**盤面から測れない条件は `undefined` を返す。** 一撃必殺（`{t:'var', name:'amount'}` =
直前に通ったダメージ）がこれで、盤面で評価すると `BindingError` になる。
ここは例外を握りつぶしているが、**勝敗を左右しない計測用の関数**なので
「黙って0にしない」の対象外とし、代わりに「測れない」ことが伝わる形（`undefined`）にしてある。

### 打ち手（`GreedyChooser`）

考えるのは2つの選択だけで、残りは `AutoChooser` に委ねる。

1. **サイクル開始の公開** — いちばん達成に近い条件を公開する（同点なら先行度の小さい方）
2. **スタックフェイズのプレイ** — 候補ごとに盤面を複製し、**そのカードを実際に解決してから**測る

2が「1手先読み」でないのは、**プレイしてもカードはスタックに乗るだけで効果は解決フェイズまで
起きない**から。1手指して盤面を見る方式ではほとんど何も見えない。
複製は `snapshot()`（`structuredClone`）で、**プレイの選択を求められる地点では
`pending` が必ず空**（直前のプレイが `drainTriggers` で流し切っている）なので取りこぼさない。

評価式は「相手のライフの減り + 自分のライフの増減×0.5 + 勝利条件の進捗×30、勝敗が決まるなら±1000」。
どれも0点以下なら**パスする**（`RandomChooser` と違って無意味な手を打たない）。

### 相手の伏せ札は見ない

`state.players[pid].objectives`（伏せてある条件）はコードからは丸見えだが、
`objectiveProgress` は**指定したプレイヤーの分しか返さない**。
相手の伏せ札を読むAIで測ると勝率が歪むため。

### この形で見つかったもの

ループ・ザ・ループが**自分自身を手札に戻して無限ループする**ことを、
目的志向AIが600戦中4戦で踏んだ（ランダムAIは3600戦回しても一度も踏んでいない）。
「勝利条件を狙う打ち手」を作る目的の半分は、こういう穴を踏ませることにある。
判断は企画側に返した（`roadmap.md` 3-0）。

## 手組みデッキ（2026-09-02）

デッキは自動生成（`sampleDeck`）をやめ、**人が書く `decks/*.txt`** に置き換えた。
自動生成は「その神のカードを定義順に一巡し、足りない分を先頭から2枚目として足す」だけで、
2枚積みになるカードがファイル内の定義順で決まっていた。バランスの数字を取る土台にならない。

### 書式をカード名にした理由

| | 名前 | ID |
|---|---|---|
| 企画側が書ける・読める | ◎ 設定シートからコピペできる | × |
| リネーム耐性 | △ 壊れるが**その場で検出**できる | ◎ |
| 実装 | 名前索引が要る（十数行） | 最小 |

**書式の顧客は人間だけ**で、機械が食べる面（`DeckList` は ID の配列）は変換で吸収できる。
名前が92枚すべて一意で、`validateDeck` の「同名3枚まで」も名前で数えていることも後押しになった。
名前が見つからないときは**行番号と部分一致の候補**を出して落とす（黙って抜けを作らない）。

JSON はデッキ編集UIが要るときに `formatDeckList` の隣へ変換を足せばよく、逆
（JSONを人が快適に手書きする）は取り返せない、という判断。

### ファイルを読む場所は1か所

- `src/engine/decklist.ts` … **純粋なパーサ**。`node:fs` に触らないのでブラウザでも動く
- `src/rules/decks.load.ts` … `readFileSync` を使う唯一のモジュール。
  将来UIをブラウザに載せるときは、ここを import しなければよい

### 対話プレイ（`tools/human.ts` / `tools/play.ts`）

**エンジンは1行も変えていない。** `Chooser` が選択の唯一の入口なので、
人間用の実装を1つ足すだけで成立する。`PerPlayerChooser` で AI と混ざり、
`RecordingChooser` で包めば人の試合もそのまま記録・再生できる。

- `HumanChooser` は**入力関数を注入できる**形にしてある（標準入力なしでテストできる）
- パイプで流し込んでも動くよう、`play.ts` 側は**届いた行を溜める**リーダーを使っている。
  `readline.question` だけだと、質問していない間に届いた行が捨てられて動かない
- 入力が尽きたら例外にする。空文字を返し続けると「選ばないことはできません」で無限に聞き直す

## デッキビルダー（2026-09-03）

ブラウザで動く1枚のHTML（`npm run builder`）。ローカルでも Artifact でも同じものが動く。

### 画面とCLIで判定をずらさない

ビルダーは**エンジンと同じ `decklist.ts` を esbuild で束ねて呼ぶ**。
画面側で枚数を数え直すと `npm run deck` と食い違うので、
「デッキをテキストにして、そのテキストを読み直せるか」だけで合否を決めている（`check()`）。
**画面で通れば必ずCLIでも通る。**

そのために `flow.ts` にあった `DECK_MIN` / `DECK_MAX` / `MAX_COPIES` / `HAND_LIMIT` を
`src/rules/limits.ts` に切り出した。`decklist.ts` が `flow.ts` を値として import していたせいで
**パーサを束ねるとエンジン約4,000行が丸ごと付いてきていた**のが、これで
`decklist + pool + errors + limits` の**5.7KB**まで落ちた（`flow.ts` からは再exportしてあるので
既存の import は壊れていない）。

### 埋め込むデータは表示に要るものだけ

`JSON.stringify(samplePool)` は効果ツリーまで入って重いので、
カードは `{id, name, god, types, text, keywords, restricted}` だけを索引にして埋め込む。
ブラウザ側の `makePool()` が `abilities: []` を補って `CardPool` の形に戻す。
パーサが見るのは名前・神・id だけなので、これで本物のパーサがそのまま動く。

### `src/browser/`

ブラウザ用バンドルに入るコードの置き場として新設した。
既存の線引き（`src/engine` と `src/rules` はブラウザ安全、`src/rules/decks.load.ts` だけが node 専用）に
「バンドルの入口」を1本足した形。ここから `node:` を import しないことが規約。

## スタックの項目にも印刷テキストを載せる

対戦画面で**スタックのカードにカーソルを合わせると効果が読める**ようにするため、
`StackItemView` に `text` と `types` を入れている（2026-09-06）。

スタックに乗ったカードは**両者に見えている**情報なので隠さない。
`itemName` で名前を出しているのと同じ扱い。
カードでも NamedAction でもない「生成された効果」には印刷テキストが無いので入らない。

## 詠唱はカードを置くたびに育つ

企画書「基本システム」の詠唱の定義:

> 詠唱を持つカードがスタックに乗せられた時、そのカードに詠唱カウンターを1個乗せます。
> **詠唱を持つカードが存在するスタックに海の神のカードが置かれるたび、
> スタック上にある詠唱カウンターをそれぞれ1増やします。**

後半が**実装されていなかった**（2026-09-06 のテストプレイで報告）。
初期値1が置かれるだけだったので、詠唱は事実上育たず、
ドレッドフル・タイダルウェイブの閾値（3/6/9）も詠唱の極致（30）も動かなかった。

`play()` の中で、カードを置いた直後に同じスタックの詠唱カウンターを1増やす（`growChant`）。

- **いま置いたカード自身は増やさない**。増やすと初期値が2になり、企画書「更新箇所」の
  「初期値は1」と食い違う
- **「海の神のカード」＝その詠唱カードのコントローラーのカード**として実装した
  （企画書「更新箇所」の書き直し「このカードが存在するスタックに**これのコントローラー**の
  カードが増えるたび」）。詠唱を持つのは海のカードだけなので、どちらの読みでも結果は同じ
- **カードを置いたときだけ**。スタックに生成された「効果」では増えない
  （効果で増やすと、増えた詠唱がまた効果を産んで自己加速する）
- カウンタの増減は `changeCounters()` の1本に通す。`counterChanged` を必ず出さないと
  閾値誘発（`thresholds`）が動かないため

**この変更でテストの前提が1つ古くなった**: AI の「詠唱をあと1つ足せば勝ち」のテストは、
種にした ドメインエキスパンション が**解決しても勝つ**（詠唱15以上で勝利）ので、
「パスして解決を待つ」でも勝ててしまい、AI がパスを選ぶのが正しくなった。
種をドレッドフル・タイダルウェイブに変えて「置かないと勝てない」盤面にしてある。

## 種族の特徴は「その種族に起きたこと」で絞る

死霊の「減った数をxとして相手にxダメージ」が、**人や天使が死んでも飛んでいた**
（2026-09-06 のテストプレイで報告）。誘発が `when: { on: 'minionDied' }` だけで、
種族の絞りが無かったため。

企画書「生命の神設定」B52 の種族一覧は

```
人間  ターン経過ごとに2倍に増える
天使  超過ダメージをすべて軽減する
死霊  減った数をxとして相手にxダメージ / ダメボ乗らず、軽減できない
魔獣  攻撃に使われるとき１体につきダメージボーナスが乗る
```

と**各行がその種族自身の特徴**なので、「減った数」は死霊が減った数と読む。
`when: { on: 'minionDied', species: { is: 'wraith' } }` にした。
`minionDied` は**種族ごとに**発火する（`damage.ts` の肩代わり・直撃、`effects.ts` の生贄の3か所とも
`species` と `count` を載せている）ので、暗黙束縛 `count` はそのまま「死んだ死霊の体数」になる。

**種族の特徴を書くときは `species` を必ず書く**——書かないと全種族の死亡を拾う。

## 自傷ダメージは軽減できない（ブレイジングラッシュ）

ブレイジングラッシュの「カードをプレイするたび2点」が、
**黒曜備え（装備数ぶん軽減）と鎧袖一触（サイクル中の軽減）で0になっていた**
（2026-09-06、seed 2185998505 のリプレイで報告）。

企画書「テストプレイ」の調整案がこう書いている:

> ①自傷は黒曜では軽減できないってやってみている。不壊くんあるしな。
> **黒曜で防げると同じターンにブレイジング2枚以上がよりやりやすくなりすぎる。**

そこで自傷に `flags: { unreducible: true }` を付けた。**無効化は別の段**なので、
不壊剛壁（`damagePrevention` / tags:'self'）はこれまでどおり効く——
企画書が「不壊くんあるしな」と書いているとおりの関係になる。

同じ調査で、**不壊剛壁が燃え盛る大地を止められない**ことも見つけた。
不壊剛壁の企画書テキストは「あなたは『ブレイジングラッシュ』と『燃え盛る大地』の効果によって
ダメージを受けない」（＝自傷ダメージを受けない）だが、
燃え盛る大地のダメージが `tags:['fire']` だけで `'self'` を持っていなかった。`'self'` を足した。

記録の再生で確認: 同じ試合で自傷が `通った 0` ×6 → `通った 3` ×6 になり、
P1 の最終ライフが 7 まで落ちる（相手の攻撃に対する黒曜備えの軽減はこれまでどおり効いている）。

**印刷テキストにも「このダメージは軽減できない。」を足した**（企画側判断・2026-09-06）。
企画書のテキスト欄（大地の神設定 E36）は「２点のダメージを受ける」のままなので、
**シートを直すのは企画側にお願いする**（こちらからは書き換えていない）。

## 解決中の項目はスタックから出せない

企画側判断（2026-09-06）で、**解決中のカードはスタックから出せない**ことにした。

解決中もカードはスタック上にあるので、そのままだと**自分自身を手札に戻せる**。
戻すと手札の枚数が減らないまま打ち直せるので、
「ループ・ザ・ループ」は1回ごとにライフを回復しながら無限に回った
（自動対戦600戦中4戦がスタックフェイズを抜けられなくなった）。
同じ穴は「熟達した跳躍」にもあり、**違いは得があるかどうかだけ**だった
（熟達した跳躍は繰り返しても何も起きないので、誰も繰り返さなかった）。

カード側のテキストを「このカード以外」に直す案もあったが、
穴を持つカードが2枚あり今後も増えるので、**ルールで閉じる**ほうを選んだ。

実装は `resolveStack` のオプション `excludeResolving`:

- **候補の段階で外す**（`{t:'choose'}`）ので「選んだのに何も起きない」にはならない
- `{t:'all'}` のように選択を伴わない指定で外れた場合は**ログに出す**（黙って減らさない）
- 立てるのは**スタックから出す効果だけ**——`moveStackToZone`（手札・墓地・追放へ）と
  `counterStack`（打ち消し）。スタック内で位置を動かす `moveStackItem` は対象外
  （スタックから出ないのでループにならない。位置の固定は `immovable` が別に持っている）
- 判定は既存の `engine.resolving`（「解決中の項目を再び解決しない」と同じ集合）

**打ち消しも間に合わなくなる**（解決に入ったカードは `counterStack` の対象外）。
これは MTG の「解決中の呪文は打ち消せない」と同じ挙動で、意図した副作用。
一方で「自分をバウンスする」意図のカードは今後書けない。

## 打ち手の評価は「積んだ時点」と「解決後」の両方で測る

`GreedyChooser` は候補ごとに盤面を複製して試し打ちする。以前は**そのカードだけを即解決して**測っていたが、
これだと**スタック上でしか成立しない条件が必ず0点**になる。
「詠唱の極致（スタックの詠唱が30）」は解決した瞬間に消えるためで、
海の打ち手が「打てるのにパス」を繰り返す原因になっていた（2026-09-06 のテストプレイで発覚）。

いまは1つの候補につき2回測る:

1. 手を打った直後（**スタックに載った状態**）— 詠唱などスタック上の価値はここでしか見えない
2. そのまま `resolvePhase` を回したあと（**解決後**）— ダメージや盤面の変化はここで出る

勝利条件の進捗は**良い方**を採る（条件は成立した瞬間に誘発するので、どちらかで満たせば勝てる）。
ライフは解決後で測る。

**パスも同じ手順で評価する。** 「何も打たずに解決したら」を基準線にして、
それ以上なら打つ（**同点ならプレイ**——パスはそのフェイズ中ずっとパスになる不可逆な選択なので）。
固定しきい値と比べる作りをやめたのはこのため。

**相手の公開済み勝利条件の進捗も引く**（`opponentWeight`、既定15）。伏せ札は見えないので見ない。

### スタックに置くこと自体を加点する（`onStackWeight`）

ドレッドフル・タイダルウェイブは**詠唱1で置くだけなら0点**で、
あとから蓄積の魔水で3/6/9に押し上げて 2/5/13点になる。
1枚ずつの評価では「置く価値」が出ないので、打ち手はこれを最後まで抱えて死に札にしていた。

`active:'onStack'` の能力を持つカードを置いたときに定数を足す（既定1）。
**カード名ではなく DSL の形で判定する**ので、AI 側に個別カードの知識は入らない。
実測（海の火力デッキ20試合）: 置いた回数 4→25、押し上げ成功率 50%→56%、1試合の与ダメ 17→23。

### 深いロールアウトは「中の打ち手」が悪いと効かない

「スタックフェイズの続きを打ち切ってから測る」（`rollout:'phase'`）も実装したが、
**どの形でも弱くなった**（AI同士で 39.6〜49.3%）。
続きを埋める打ち手が雑（打てるなら手札の先頭）なので、
候補ごとに違う「ありもしない続き」で採点してしまうため。
**探索を深くする前に、中で使う打ち手の質を上げないと意味がない。**
コードは残してあるが既定は `'stack'`。

### 測って捨てた案

| 試したこと | 結果 |
|---|---|
| 同点より少し損でも打つ（`passThreshold` を負に） | AI同士192戦で 51.6%。強くならない |
| 伏せ札の重みを 0.5→0.25 / 0.1 | 50%。海はむしろ弱くなる（手札を抱える判断が消えるため） |
| 妨害の重みを 15→30 | 48.4%。いまの勝利条件は1手で相手の進捗が動かない |

新しい評価は**変更前の評価に AI同士192戦で 61.5%**、
ランダム相手の勝率は **50.2% → 63.2%**（600戦・先後入れ替え）。
コストは `npm run simulate -- --games 600 --compare` で約2分30秒。

**残る限界**: 海のパスは半分しか減らない。「叡智の飽和（手札ちょうど15）」があるため
カードを使うと進捗が下がり、**プレイが本当にマイナス点**になる。
1手先の評価としては正しい判断で、直すには複数サイクルを見る探索が要る。

## 「与えたダメージ」を数える条件は、当たった相手で絞る（`countEvent.to`）

十連撃の誓約「あなたが10回目のダメージを与えたなら、勝利する」を
`countEvent(damageDealt, by:self)` だけで書いていたため、**自傷まで数えていた**。

ブレイジングラッシュの「このサイクルが終わるまで、あなたはカードをプレイするたび2点のダメージを受ける」は
自分が自分に与えるダメージなので `damageDealt(player=自分)` が積まれる。
しかもこれは**プレイのたび**に誘発するので、解決フェイズを待たずに数が伸びる——
2枚出したあと3枚プレイしただけでカウント9まで行き、
**スタックフェイズ中に勝利条件が成立**していた（2026-09-06 のテストプレイで発覚）。

`countEvent` に **`to`（当たった相手）** を足し、この条件は `to:'opponent'` にした。
企画書「基本システム」の原文は「槍連打・戦技で刺突・**n回命中したら**」という攻撃回数の文脈なので、
自傷を数えないのが読みどおり。

**瞬発カードがスタックフェイズ中にカウントを進めるのは正しい**（瞬発は即時解決するため）。
インスタントフォージで槍を作れば、その場で刺突2回ぶん数える。

## 案の段階のものを実装しない（企画書④パッシブ能力案）

企画書「基本システム」の**④パッシブ能力案は案の段階**なので実装しない（2026-09-06 企画側判断）。
大地の神に入っていた2つを削除し、**大地のパッシブは無し**になった。

- ①攻勢＝あなたの与えるダメージと受けるダメージは＋1
- ②難攻不落＝あなたのターン開始時、シールド5を得る

入っていたせいで、テストプレイで次の食い違いが出た:

- 刺突が `1+1` ではなく `2+2`（`amount:1, times:2` の各ヒットに +1 が乗るため）
- ブレイジングラッシュの自傷が 2点ではなく **4点**（自傷は与える側も受ける側も自分なので、
  与ダメ+1 と 被ダメ+1 の**両方**が乗る）

**ダメージがサイクル数ぶん増える規則（サイクルダメージボーナス）は別にあり、実装済み**
（`damage.ts` の段2 `v += s.cycle`）。企画書「基本システム」の
「ほぼ全てのカードは常にサイクル数に等しいダメージボーナスが与えられる。つまり開始時はボーナス0」がそれで、
除外は `flags.ignoreCycleBonus` / カードの `ignoresCycleBonus` / `ignoreCycleBonus` の継続的効果 /
雨・豪雨 / 天候タグの5経路。**パッシブで打点を底上げして代用しない。**

生命の神の「サイクル開始時に全種2体」は④案ではなく企画書「基本ルール」のフェイズ注釈
（「①サイクル開始フェイズ（…生命ログインボーナスでミニオン2体…）」）が根拠なので、こちらは残っている。
海の「予知領域」も④案に項目があるが、**パッシブではなくゾーン**としてカードが直接使っているので対象外。

## 「このカードが生成されたとき」は自分自身に限る

誘発の `subject` を省略したときの既定は「このカード自身 / 自分に起きたこと」だが、
判定が `ev.itemUid`（スタック項目）と `ev.player`（プレイヤー）しか見ておらず、
**トークンについては「同じプレイヤーに起きたか」だけ**になっていた。

その結果、ヴァーミリオンピアス（槍）の
「このカードが生成されたとき刺突を行う」が、**別の装備を作るたびに**誘発していた
（インスタントフォージで剣を作っただけで刺突が飛ぶ）。

`TriggerSource` に `tokenUid` を持たせ、**イベントがトークンについてのもの（`bindings.token` を持つ）なら
そのトークン自身に限る**ようにした。トークンの能力でも `damageTaken` のような
トークンを主語にしないイベントは、これまでどおりプレイヤーで判定する。

## 手札を直接押して選べるのは「プレイの選択」だけ

対戦画面は「手札のカードを押す＝そのカードをプレイする」ようにしてあるが、
判定が**プロンプトの選択肢名と手札のカード名の一致**だけだった。
そのため「手札からn枚選ぶ」（テラブレイズ・リビルド）でも手札が押せてしまい、
1枚目を押した瞬間に送信されて選び終わる前に次へ進んでいた。

`PendingRequest.play` を足し（サーバ側で `prompt === PLAY_PROMPT` のときだけ立てる）、
画面はその印があるときだけ手札を押せるようにした。
**画面にエンジンを import させないための印**でもある（`PLAY_PROMPT` を持ち込むと
`flow.ts` 経由でエンジンごとバンドルに入る）。

## サイクルは0起点（企画書「基本ルール」）

**最初のサイクルは0サイクル目**で、そこで引く7枚が初期手札。企画書のドロー表が
「0サイクル目＝7枚（初期手札）／1サイクル目＝5／2＝6／3＝7／4＝5／5以降＝1」と定義していて、
累計 7/12/18/25/30 で**4サイクル目にちょうど30枚を引き切る**ように配分されている。

以前の実装は `startGame` で7枚配ってから**プレイさせずに**1サイクル目へ進み、
そこでさらに5枚引いていた。つまり**0サイクル目のスタックフェイズが丸ごと無かった**ため、
最初のプレイが手札12枚で始まっていた（2026-09-06 のテストプレイで発覚）。

直し方は「0サイクル目を他と同じ1つのサイクルとして回す」だけにした:

- `startGame` は**配らない**。デッキの検証・シャッフル・勝利条件を伏せるところまで
- `startGame` は `cycle`（と `turn`）を **-1** に置く。`startCycle` が先頭で +1 するので、
  最初のサイクルが 0 になる。-1 が外から見えるのは `runGame` に入るまでの一瞬で、
  その間に `Chooser` を呼ぶ処理は無い
- 7枚は0サイクル目のドローフェイズで引く。**公開特殊勝利条件のオープンが先**（①→②の順）なので、
  0サイクル目だけは「手札0枚で1つ公開してから7枚引く」形になる

副作用として**終末の発生が正しくなった**。`endCycle` の `if (s.cycle >= 2)` は
企画書の「2サイクル目の終了フェイズ」を指すつもりの式だったが、
1起点で数えていたぶん**1サイクル早く**終末が来ていた。0起点になったことで式がそのまま仕様と一致する。

記録の版（`RECORD_VERSION`）は 2 に上げた。0サイクル目のぶん選択の並びが変わるので、
v1 の記録は再生できない（保存済みの対戦部屋も同様に続きから遊べない）。

退行テストは `flow.test.ts` の
「最初のプレイは0サイクル目・手札7枚」「終末は2サイクル目の終了フェイズに加わる」の2件。

## 遠隔対戦（`src/engine/view.ts` / `src/net/` / `api/` / `src/browser/`）

手順とVercelの設定は `docs/deploy.md`。ここには**なぜこの形にしたか**だけ残す。

### 対戦の実体を「選択の列」にした

サーバ（Vercel Functions）は常駐せず、呼び出しをまたいで何も覚えていない。
一方このエンジンは乱数が `GameState.rng`（シード付きLCG）**だけ**で、
`Math.random` も時刻も使っていない。よって **`(セットアップ, シード, 選択の列)` が同じなら
盤面は完全に再現できる**。保存するのは `GameRecord` そのものにした。
副作用として、対戦中の部屋をそのまま `npm run replay` に渡せる。

### 「次の選択で止める」は例外で実現する

`runGame` には中断の口が無い。**記録が尽きたら `Chooser` が例外を投げればよい**——
呼び出しスタックが畳まれて `resumeGame` まで戻り、`engine.state` は
**その選択を求めた瞬間の盤面**のまま残る。これがそのままビューになる（`src/net/resume.ts`）。

「途中の盤面を保存して再生を短縮する」は**できない**。いまどのフェイズのどのループにいるかは
JSのコールスタック上にあって `GameState` には無いため、状態を保存しても再開できない。
再生は毎回頭からになるが、選択のたびに1回で済むので費用の問題にならない
（1試合まるごとで 0.2 秒。`src/net/cost.test.ts` が毎回実測して出す）。

### 経路を分けて、ポーリングにエンジンを載せない

1試合のポーリングは数百〜千回、選択は数十回。**回数が2桁違う**ので経路自体を分けた。

| 経路 | 中身 | エンジン |
|---|---|---|
| `GET /api/v` | 版番号1つ（Redis の別キー） | import すらしない |
| `GET /api/state` | 保存済みのビュー | 回さない |
| `POST /api/game` | 選択を足して再生 | 回す |

「今は呼んでいない」ではなく「そもそも import されていない」ところまでテストで見ている
（`src/net/routes.test.ts` が `server/functions/v.ts` から実行時に辿れるファイルを走査する）。

### 隠された情報は削るのではなく組み立てる

`GameState` から不要なものを消す作りにすると、消し忘れがそのまま情報漏れになる。
そのまま配ると漏れるのは相手の手札だけではない:

- `state.rng` … **以後のシャッフルとランダム選択が完全に予測できる**
- `limitUses` … キーが `objective:<player>:<id>` 形式なので**伏せた勝利条件のIDが露出する**
- `events[].bindings` / `snapshots` … 引いたカード・探したカードの実体が入る

そこで `playerView()` は**ホワイトリストでしか値を積まない**。`GameState` にフィールドが増えても、
ここに書かない限り外に出ない。`src/engine/view.test.ts` が
「ビューのJSON文字列にそれらが現れないこと」を毎回確かめる。

### 割り込みは「何手目か」で弾く

応答には `index`（＝ここまでに記録された選択の数）を添えてもらい、
**`index === choices.length` のときだけ適用する**。二重送信も、遅れて届いた古い応答も、
これだけで弾ける（ロックを取らない）。**手番の判定より先に手数を見る**——
再送はそのあいだに手番が移っていても「古い応答」として素通しにしたいため。

### 自分の手番でもポーリングを止めない

止めると、選択を送った応答が届かないまま切れたとき
「こちらは手番のつもり・サーバは先へ進んでいる」で噛み合わなくなり、リロードするまで戻れない。
版番号を見に行くだけなら安いので、自分の手番のあいだは15秒に1回だけ心音を打つ
（`src/browser/net.ts` の `SELF_TURN_MS`）。

### 席の控えはタブごとに持つ

いま座っている席は sessionStorage（タブごと・リロードでは残る）、
控えは localStorage に `部屋:席` の鍵で残して入口に「戻る」ボタンとして出す。
localStorage に「部屋コード → 席」の表を1つ置く作りだと、
**同じブラウザの2つのタブで同じ部屋に入ったとき、2席目が1席目の身分証を上書きする**。

### 同神対決はロビーで弾く

ルール上起こらない組み合わせなので、デッキ選択の時点で断る
（`determineFirst` の `RuleError` まで行くと、対戦が始まった瞬間に部屋が壊れる）。
AI の席も、相手と違う神のデッキを選ぶ。

### `targetCheckDepth` をモジュール変数から `Engine` へ移した

`continuous.ts` の再入防止フラグがモジュール変数だった。`await` を挟むので、
**1プロセスで複数の対戦が並ぶと `untargetable` が黙って効かなくなる**。
サーバでは1プロセスに複数の部屋が乗るため、`Engine` のフィールドに移した。

## まだ手を付けていないところ

- 待機値・優先度（保留のまま）
- トークンの `unique` / `maxCopies` を `createToken` が見ていない
- `RandomChooser` は「山の番号」を聞かれる場面で範囲外の数を返しうる（実害は出ていない）
