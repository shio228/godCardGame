# 解決エンジン実装メモ（v1）

`src/engine/` に `resolve(effect, ctx)` のインタプリタを実装した。
設計書 `rule-engine-design.md` の確定事項をそのままコードに落としたもので、
DSL 側（`src/rules/types.ts`）への変更は `countEvent.measure` の追加1件のみ。

```
npm run typecheck   # tsc --noEmit（strict + exactOptionalPropertyTypes）
npm test            # ゴールデンテスト 72件（うち勝利条件のエンジン20件・データ27件）
npm run sweep       # 全92枚を空盤面で走らせ、落ちるカードを一覧にする煙テスト
```

## ファイル構成

| `context.ts` | `Engine`（1ゲーム分の可変環境）と `Ctx`（効果1つ分）、束縛スコープ |

| `value.ts` | `Value` の評価 |
| `condition.ts` | `Condition` の評価 |
| `select.ts` | 各セレクタの評価とフィルタ判定 |
| `continuous.ts` | `ContinuousMod` の収集（神/スタック/場/付与/勝利条件パッシブの5経路）と対象不可判定 |
| `damage.ts` | ダメージパイプライン11段と `changeLife`（置換効果の唯一の通り道） |

| `flow.ts` | `createEngine` / `play` / `resolvePhase` / `startCycle` / `endTurn` |

## 実装で決めたこと

### 1. 選択は async/await + `Chooser`

`resolve` は `Promise` を返し、選択は `await ctx.engine.chooser.select(...)` で待つ。
テストは `ScriptedChooser`（応答を配列で与える）、ランダム対戦は `AutoChooser`、
UI は「クリックで解決される Promise」を返す実装を差し込む。

代償として**解決の途中状態はシリアライズできない**。リプレイや巻き戻しを
解決の粒度で行いたくなったら、ジェネレータ（`yield` で中断）への移行が必要になる。
いまは `snapshot()` を効果の境界で取る運用で足りる想定。

### 2. 状態はミュータブル + `structuredClone` のスナップショット

`GameState` を直接書き換える。テスト・巻き戻しは `snapshot()` / `restore()`。

### 3. 未対応ノードは必ず例外

`NotImplementedError` / `RuleError` / `BindingError` / `LoopError` を用意し、
黙って何もしない経路を作っていない。束縛名の解決失敗も 0 に落とさず例外にする。

### 4. 置換効果は必ず1本の経路を通る

- ライフの増減はすべて `changeLife()`（根性 = `lethalReplacement` がここで働く）
- ドローはすべて `drawCards()`（`drawDelta` がここで働く）
- ダメージはすべて `dealDamage()`

直接 `p.life -= x` や `hand.push(deck.pop())` を書ける場所をエンジン内に作っていない。

### 5. 誘発の順序（暫定規約）

設計書 §10 の宿題に対する現在の実装:

1. イベントは即座に誘発を実行せず `engine.pending` に積む
2. `drainTriggers` が **先攻プレイヤー → 後攻プレイヤー** の順に流す
3. 同一プレイヤー内に複数あるときは `chooser.order` で本人に順序を選ばせる
4. 処理中に積まれた誘発は同じループで続けて処理する

### 6. 無限ループ検出

`engine.budget`（既定10000ステップ）を超えたら `LoopError`。
加えて `engine.resolving` で「解決中の項目を再び解決しない」ようにしている
（これがないとスプリットディメンションの `resolveStack {t:'all'}` が自分自身を
巻き込んで無限再帰する）。

## 企画側で確定した仕様（2026-08-30）

1. **詠唱カウンターの初期値は1**。「プレイしたとき詠唱カウンターを**さらに**5つ置く」
   という文面どおり、`chant` キーワードを持つカードはプレイ時に1つ乗った状態で始まる。
   アンプリファイバブルシールドの軽減量は 6 から始まる。
2. **ミニオンは1点=1体で消える**。体力を持たない仕様なので、割り振られたダメージ1点につき
   1体が失われる。防御指令・天使の吸収量がこれで決まる。
3. **常在を持つ NamedAction は「乗せた時点」から働く**。防御指令の効果は
   `grantContinuous(duration:'whileOnStack')` なので、解決時に実行したのでは
   その瞬間に消えてしまう。効果が whileOnStack の付与だけで構成されるアクション項目に限り、
   配置時に付与を実行している。
4. **引き切りペナルティで敗北したらそこでゲームが終わる**。不足2枚なら
   「30点のダメージを受ける」が2つスタックに積まれるが、1つ目でライフが0になった時点で
   勝敗が決まり、2つ目は解決されない。
5. **`countEvent` は `measure` で数え方を必ず明示する**（下記）。

## `countEvent.measure`（必須フィールド）

「回数」と「数量」は、**効果は起きたが数量が0だった**場面で結果が割れる
（軽減しきったダメージ / ミニオン0体での攻撃指令）。既定値を置くとどちらの読みか
分からなくなるので、`measure` を必須にして毎回書かせる。

| 値 | 意味 | 例 |
|---|---|---|
| `'events'` | イベントの発生回数。1イベント = 1 | 「天候が5回変わったなら」 |
| `'units'` | イベントが表す数量の合計（点数 / 体数 / 枚数） | 「死亡したミニオンに等しい数」「ダメージを受けていないなら」 |

`GameEvent.units` がその数量を持つ。damageDealt の units は
**「与えたダメージ」（修正込み・軽減前）**、damageTaken の units は
**「実際に通ったダメージ」** — 設計書 §5 の用語に合わせている。
`granularity: 'perUnit'` の反復数も同じ `units` を見る。

現時点のカード92枚での使い分け（`countEvent` は7箇所）:

| カード | イベント | measure |
|---|---|---|
| リアクティブアクアスフィア | damageDealt | `units` |
| 栄光の凱旋 | damageDealt | `units` |
| フローレスフェザー | damageTaken | `units` |
| 犠牲の残り香 | minionDied | `units` |
| 最期の献身 | minionDied | `units` |
| 明鏡止水 | weatherChanged | `events` |
| セレスティアル・ディザスター | weatherChanged | `events` |

`drawn` を `countEvent` で数えるカードはまだ1枚もない。

**`countEvent.by` は「そのイベントの主体」**と照合する（`GameEvent.player`）。
damageDealt なら与えた側、damageTaken なら受けた側、drawn なら引いた本人、
minionDied なら持ち主。加害者を引きたいときのために `GameEvent.dealer` を別に持っている。

### この作業で見つかったデータ側の不具合

**犠牲の残り香**の `countEvent` が `of: { t: 'self' }` を渡していた。
`countEvent` に `of` というフィールドは無く、`as never` でキャストして
型チェックをすり抜けていた（`countSpeciesKinds` からのコピーと思われる）。
`by: { t: 'self' }` に直してキャストを外した。
**`as never` / `as any` はDSLの穴を隠すので、今後は入れない。**

## 現状のカバレッジ

`npm run sweep` = **85 / 92 枚**が空盤面で最後まで走る。残り7枚の内訳:

- handler 未登録が3枚（並列思考 / スタック分割 / ケイオス・フォーチュン）

- プレイ条件・タイミングを満たしていないだけが4枚

## 特殊勝利条件（`objectives.ts`）

企画書「基本システム / 基本ルール」のルールをそのまま実装した。

### 公開と先攻決定

- `setupObjectives(engine, player, ids)` … 採用した条件を伏せてセットする。
  **3つ未満・他の神の条件・先行度の重複**をここで弾く
  （「先行度は同じ数字を持たない」を、先攻決定が引き分けになる前に検出する）。
- `revealPhase(engine)` … ①サイクル開始フェイズの公開。`startCycle` の先頭で呼ぶ。
  **両者の選択を先に集めてからまとめて公開する**。1つずつ公開すると後に選ぶ側が
  相手の先行度を見てから決められてしまい、「見せあって決める」というルールにならない。
- `determineFirst(engine)` … 両者が**最後に公開した**条件の先行度を比べ、
  1に近い方を先攻にする。公開し尽くしたサイクル3以降は公開が起きないので、
  「最後の数値で固定」は特別な分岐なしにそのまま成り立つ。
- 公開は `objectiveRevealed` イベントとして誘発できる（`GameEvent.objectiveId` に id が載る）。
  カード効果 `revealObjective` もこの経路を通るが、**先攻は決め直さない**
  （先攻が動くのはサイクル開始の公開だけ）。

### 判定は2経路

`ObjectiveDef.when` の形で分かれる。

| `when` | 経路 | 実装 |
|---|---|---|
| `TriggerEvent` | 通常の誘発とまったく同じ | `events.ts` の `gatherSources` が第5の発生源として拾う |
| `{ on: 'continuous' }` | 状況起因判定 | `checkObjectives` が安全地点ごとに走査する |

`ObjectiveDef.cond` は誘発型では `TriggerEvent.cond` に合流させる（両方あれば `and`）。
`effect` を省略した条件は **「その条件の持ち主が勝利する」** の意味になる。
`passive` は公開されている間だけ効く `ContinuousMod` で、`gatherMods` の⑤番目の発生源。

### 判定地点は `drainTriggers` の1か所だけ

`checkObjectives` の呼び出しは `drainTriggers` の先頭にしか置いていない。
プレイ後・スタック項目の解決後・各フェイズはすべて `drainTriggers` を通るので、
呼び忘れで判定が漏れる場所を作らずに済む。`drainTriggers` は
「pending が空でも1周は回る」形に変えてある。

### ここで決めた仕様（4点とも企画側の承認済み・2026-08-31）

1. **状況起因の判定は安全地点でのみ行う**（MTGの状況起因処理と同じ）。
   ひとつの効果の途中で一瞬だけ条件が成立しても勝利しない。
   例: 「ライフがちょうど35なら勝利」は、5点回復してから100点回復する効果では成立しない。
2. **`when: {on:'continuous'}` の条件は既定で1ゲームに1回だけ発火する**
   （`CONTINUOUS_DEFAULT_LIMIT`）。成立している間ずっと真なので、
   制限がないと判定のたびに発火してしまう。繰り返したい条件は `limit` を明示する。
   → このために `ObjectiveDef.limit?: Limit` を1フィールドだけ追加した（DSLの変更はこれだけ）。
   代案（`limit` を必須にする／条件が偽に戻ったら枠を戻すエッジ検出）は検討のうえ不採用。
3. **`initiative: 'special'`（創造の特殊枠）は最後尾扱い**。数値と比較できないため。
   'special' 同士なら前サイクルの先攻を維持する。企画側で数値が決まればこの分岐は消える。
   創造の神は調整中のため、当面この扱いのままにする。
4. 数値の先行度が両者で並んだら `RuleError`。「先行度は一意」というルールをデータの誤りとして扱う。

### 条件データ（`src/rules/objectives.sample.ts`）

企画書「基本システム」C55〜C111 の一覧から、**先行度の仮配分が振られている各神3つずつ**を
データ化した（計12件、`samplePool.objectives`）。

| 神 | 先行度 | 条件 |
|---|---|---|
| 大地 | 1 | 十連撃の誓約 — 10回目のダメージを与えたなら勝利 |
| 大地 | 3 | 完全武装の証明 — 武器3種・防具2種をコントロールし打撃でダメージを与えたなら勝利 |
| 大地 | 6 | 一撃必殺 — 1度の攻撃で8点のダメージを与えたなら勝利 |
| 生命 | 2 | 生命の氾濫 — ターン開始時にライフ99以上なら勝利 |
| 生命 | 8 | 生死の振幅 — お互いのライフが50回以上変動したら勝利 |
| 生命 | 12 | 万象の軍勢 — 4種類それぞれ5体以上コントロールしているなら勝利 |
| 空 | 4 | 無限連鎖 — 自分の効果が一度に15個スタックに乗ったら勝利 |
| 空 | 7 | 天象二十変 — 累計20回天候が変わったら勝利 |
| 空 | 9 | 連鎖する空 — 自分の項目がスタック上で7つ連続したら勝利 |
| 海 | 5 | 詠唱の極致 — スタック上の詠唱合計が30以上で勝利 |
| 海 | 10 | 叡智の飽和 — ターン終了時に手札ちょうど15枚で勝利 |
| 海 | 15 | 完全なる水位 — ターン開始時にライフちょうど35で勝利 |

先行度は 0〜15 のうち創造の 0/11/13/14 を除いた12個で、**全神を通して一意**
（`objectives.data.test.ts` が総当たりで検証している）。

データ化で判断した点は各条件の `note` に書いた。企画側の判断が入ったのは次の3つ（すべて確定）。

1. **一撃必殺の「8点」は軽減後（実際に通ったダメージ）で判定する。**
   暗黙束縛 `amount` がその値なのでそのまま使っている。設計書§5の用語では「与えたダメージ」は
   軽減前だが、ここは「相手が軽減で防げる＝対策の余地がある」側を採った。
2. **十連撃の「10回」は0点だったダメージも1回と数える。** `measure:'events'` の性質そのまま。
   企画書には「0ダメでも数えるから納得いかないかも」というコメントがあったが、これでよいと確定。
3. **生命の「5種類以上の種族」は「4種類それぞれ5体以上」に読み替えた**（企画書のアレンジ案）。
   ミニオンは人間・天使・死霊・獣の4種類しかなく原文のままでは達成不可能なため。
   **5体はテスト段階の仮の数値**で、変わる前提。

もうひとつ、企画側の判断ではないがデータ化で決めた点として、
**「武器3種類・防具2種類」は名前で1つずつ検査している**。`countTokens` の `kind` は個数を数えるので、
剣（maxCopies:3）を3つ持つと「武器3種類」になってしまうため。装備の種類が増えたらここも直す。
同じ理由で「4種類それぞれ5体以上」も種族を書き並べている
（盤面の種族種類数を数える `Value` が DSL に無い）。

### 見送った候補

- 海「40枚デッキで引き切ったら敗北の代わりに勝利」— 引き切りペナルティは即敗北ではなく
  「30点ダメージをスタックに追加」なので噛み合わない。デッキ構築制約の表現も無い。
- 海「天候が雨の状態が2サイクル継続」— 企画書に「どこで判定するか」と未決の書き込みあり。
- 海「4つの場所からカードを手札に加えた」— カードの由来ゾーンを追跡する仕組みが無い。
- 空「手札7枚で始まったターンに手札0でカウンター、3以上で勝利」— 企画書に「不可能っぽい」とある。
- 生命「このターン終了時にミニオン合計数が40（仮）以上なら」— 書けるが先行度の枠が埋まった。
- 大地「このターン発生したダメージを全て0まで軽減できたら勝利」— 書けるが先行度の枠が埋まった。
  「一度もダメージを受けていない」場合も成立してしまう点も要判断。
- 数値未定のもの（生命「ミニオンをn体以上」×2、海「除外枚数n以上」）。

### まだ無いもの

- 創造の神の特殊な公開ルール（企画側で調整中）。
  （「複数選んで最も先行度の低いものだけ公開」「この勝利条件は公開できない」
  「先行度0＝他を選べず必ず先攻・初期手札5枚」）。
  現状の穴: `initiative:'special'` の条件も `revealPhase` の選択肢に普通に並ぶ。
  本来はサイクル開始では選べず、条件が成立したときに自動で公開されるべきもの。
  先行度0 の条件は `setupObjectives` に `min: 1` を渡さないと「3つ未満」で弾かれる。
  伏せる／指摘する系の効果も DSL に無い。
- 勝利条件を**伏せ直す**効果（企画書に言及あり）。
