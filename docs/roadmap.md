## いま出ている数字（`npm run simulate -- --games 600 --seed 100 --compare`）

**手組みデッキ（`decks/*.txt`）で取り直した数字。** 以前の自動生成デッキの数字とは比較できない。
打ち手は2種類で、**ランダム**は一様ランダム（何も考えない基準値）、
**目的志向**は勝利条件の進捗と相手ライフを見て選ぶ（`ai.ts`）。
どちらも1手ずつの評価しかしないので、**プレイングの上限ではなく下限**の数字。

```
                        ランダム    目的志向
平均決着サイクル            1.88      1.69
先攻の有利さ（補正後）      +5.8pt   +13.3pt
特殊勝利で決着             22.2%     34.0%
神の総合勝率  大地          51.0%     85.0%
              海            7.3%     20.7%
              空           64.0%     35.0%
              生命         77.7%     59.3%
直接対決（目的志向 vs ランダム、先後入れ替え600戦）… 目的志向の勝率 69.8%
```

読み取れること:

- **決着が速すぎる。** 平均1.7〜1.9サイクルで、設計目標の3に届いていない。
  自動生成デッキ（平均2.0〜2.3）より短くなったのは、手組みのほうが主力を3枚積むぶん打点が濃いため。
  **ライフ30が少ないか、打点が高い**。ここは数値調整の判断が要る
- **後攻有利仮説はここでも否定される**が、**前回とは逆に「打ち手が良くなるほど先攻有利が強まる」**
  （+5.8pt → +13.3pt）。自動生成デッキでは逆の傾向（+13.9pt → −6.3pt）が出ていたので、
  **この指標はデッキ構成に強く依存する**。先攻後攻のルールを変えるかどうかは、
  デッキが固まってから決めるべき
- **大地アグロが強すぎる**（目的志向で85%）。速い決着と噛み合っている
- **海は依然として弱い**（7〜21%）。勝ち筋が「叡智の飽和」に偏っている点は変わらない
- **空はランダムだと強く（64%）、目的志向だと弱い（35%）**。
  勝ち筋の「連鎖する空（7つ連続）」が達成率13.2%→3.5%と落ちるためで、
  **相手が無駄な手を打たないと成立しない**構造がはっきり出ている

### 勝利条件は「届かない」のか「踏んでいない」のか

達成率と、達成できなかった試合も含めた**到達度**（`cond` を盤面で評価した0〜1）を並べる。

| 条件 | 達成率(乱→目) | 到達度の平均(目) | 読み |
|---|---|---|---|
| 十連撃の誓約 | 3.2% → 15.2% | 84% | 機能している |
| 叡智の飽和 | 0.3% → 7.3% | 84% | **狙えば届く** |
| 万象の軍勢 | 3.3% → 7.5% | 59% | 機能している |
| 連鎖する空 | 13.2% → 3.5% | 21% | 相手依存（上記） |
| 完全武装の証明 | 0% → 0% | 45% | **あと一歩**。装備5種を1試合で揃えきれない |
| 天象二十変 | 0% → 0% | 28% | 20回は多すぎる |
| 生命の氾濫 / 生死の振幅 | 0% → 0% | 28% / 21% | 99ライフ・50回変動とも**試合が短すぎて届かない** |
| 完全なる水位 | 0.8% → 0.3% | 21% | ライフをちょうど35に合わせる手段が乏しい |
| 無限連鎖 | 0% → 0% | 7% | 効果15個は遠い |
| 詠唱の極致 | 0% → 0% | 1% | **ほぼ動かない**。詠唱30は現状のカードで積めない |
| 一撃必殺 | 1.3% → 0.2% | 測れない | 盤面ではなく「直前のダメージ」を見る条件 |

到達度は**デッキの組み方でも動く**（詠唱を厚くすれば詠唱の極致は伸びる）。
数値を変える前に、まず `decks/sea.txt` を詠唱寄りに振って測り直すのが安い。

## 優先度1: 企画側の判断が要る数字が出そろっている

上の表がそのまま議題になる。エンジン側の実装は不要で、**決めれば数字を取り直せる**。
デッキも `decks/*.txt` を書き換えるだけなので、**案を出す → 30分で数字が出る**回り方ができる。

1. **決着が速すぎる**（平均1.7〜1.9サイクル、目標3）。ライフ30を上げるか、打点を下げるか
2. **届いていない勝利条件の数値を下げるか、条件を変えるか**
   （天象二十変20回 / 生命の氾濫99 / 生死の振幅50回 / 無限連鎖15個 / 詠唱の極致30）。
   `objectives.sample.ts` の数値を変えて `npm run simulate -- --compare` を回せば即座に効果が見える
3. **海の勝ち筋を増やすか**（現状ほぼ「叡智の飽和」1本）
4. **大地が強すぎないか**（目的志向で85%）。デッキの問題かカードの問題かは、
   `decks/earth.txt` を弱めて測り直せば切り分けられる
5. **先攻後攻**: デッキ構成で符号が変わるので、**デッキが固まるまで判断を保留**するのが安全

上の数字で「打ち手が良くなるほど先攻有利は消える」方向が見えているので、優先度は下げてよい。

## 優先度3: 残っている仕様の穴

いずれも企画側の判断が要るもの。**実装は判断が出てから。**

### 3-0. ループ・ザ・ループの無限ループ（目的志向AIが発見）

「あなたの手札に等しい枚数まで、スタックからあなたのカードを手札に戻す。
これにより手札に戻したカードの枚数に等しいライフを回復する」＋**瞬発**。

このカードは解決中もスタック上にあるので、**自分自身を手札に戻せる**。
戻すと手札の枚数が減らないまま再びプレイでき、1回ごとにライフが回復する。
600戦中4戦がこれでスタックフェイズを抜けられなくなった（`RuleError` で止まるので
エンジンは壊れないが、その試合は決着しない）。

**エンジン側では直していない。** 決め方が2通りあるため:

| 案 | 内容 | 影響 |
|---|---|---|
| A | カードのテキストを「このカード以外」にする | このカード1枚で閉じる。データ修正だけ |
| B | ルールとして「解決中のカードは自分自身の効果で移動できない」 | 全カードに効く。既存の「解決中の項目を再び解決しない」と揃う |

Bにすると「自分をバウンスする」意図のカードが今後書けなくなる点に注意。

### 3-1. 創造の神の特殊な公開ルール

前回から変わらず。「複数選んで最も先行度の低いものだけ公開」「この勝利条件は公開できない」
「先行度0＝他を選べず必ず先攻・初期手札5枚」。
現状 `initiative:'special'` は最後尾扱いの暫定処理で、`revealPhase` の選択肢に普通に並ぶ。
**創造は勝利条件が未データ化なので、`sampleDeck` / `simulate` の対象外**（`PLAYABLE_GODS`）。

### 3-2. 勝利条件を伏せ直す効果

企画書に言及はあるが DSL に無い。前回から変わらず。

### 3-3. トークンの `unique` / `maxCopies` が効いていない

`TokenDef` に「これは1つしか装備できない」「同じ装備は3つまで」があるが、
`createToken` はどちらも見ていない。**黙って上限を超える。**
生成候補が尽きたときは何も作らない（例外にしない）ようにしたが、上限側は未実装のまま。

## デッキ構築（手組み）

デッキは `decks/*.txt` に人が書く。書式はカード名指定のテキスト。

```
# 大地 / アグロ            ← 行頭 # はコメント。狙いを書いておく
god: earth                 ← 必須
objectives: 十連撃の誓約, 完全武装の証明, 一撃必殺   ← 省略するとその神の全条件
3 紅蓮着火                 ← 「枚数 カード名」。枚数省略で1枚
```

```
npm run deck                      # decks/ を全部検証
npm run deck -- decks/earth.txt   # 1つを詳しく（勝利条件・タイプ内訳・内訳）
npm run deck -- decks/earth.txt --text   # 各カードの印刷テキストも
npm run builder                   # ブラウザで組む（tmp/deckbuilder.html）
npm run builder -- --fragment     # Artifact 公開用
```

### デッキビルダー（ブラウザ）

カードのテキストを見ながら枚数を調整し、その場で検証して `decks/*.txt` に貼れるテキストを出す。
**リポジトリを持っていない人（企画側）でも Artifact のURLだけで触れる。**

- 左に神ごとのカードプール（名前・テキスト・タイプで検索、タイプで絞り込み、`＋`/`−` で枚数）
- 中央にデッキ（枚数ゲージ・勝利条件の選択）、右に検証と内訳（タイプ別・キーワード・プレイ制限つき枚数）
- 下にデッキリストのテキスト（コピー）と、貼り付けて読み込む欄。`decks/` の4デッキは同梱してある
- **合否の判定はエンジンと同じパーサ**（`decklist.ts`）を esbuild で束ねて画面から呼んでいる。
  画面で通れば `npm run deck` も必ず通る（別々に数え直すとズレるため、そこは共有した）

- **カード名で書く。** 92枚すべて名前が重複しておらず、`validateDeck` の「同名3枚まで」も
  名前で数えているので数え方が一致する。名前が違えば**行番号と候補**を出して落ちる
- 検査は 30〜40枚 / 同名3枚 / 神の一致 の3つ（企画書「基本ルール」）＋勝利条件の神と件数
- `npm run simulate` / `npm run play` / `npm run dashboard` はすべてこのデッキを使う。
  `--decks <dir>` で別のディレクトリに切り替えられる（案を並べて比較するとき）
- **初期の4デッキはエンジン側で組んだ叩き台**。バランスの数字はこの構成に強く依存するので、
  企画側で組み直したら数字も取り直す

## 対話プレイ

```
npm run play                                     # あなた(P1) vs 目的志向AI(P2)
npm run play -- --deck1 decks/sea.txt --deck2 decks/life.txt
npm run play -- --you both                       # 2人で交互（ホットシート）
npm run play -- --you none                       # AI同士を眺める
npm run play -- --seed 42 --record tmp/game.json # 記録して後で再生
```

選択のたびに「前回から起きたこと」「盤面」「手札（印刷テキストつき）」が出る。
`b` 盤面 / `l` ログ / `q` 投了 / `?` ヘルプ。**相手の手札の中身と伏せた勝利条件は見えない。**

人が打った試合も `RecordingChooser` を通るので、そのまま `npm run replay -- --in` で
再生でき、ダッシュボードのリプレイにも載せられる。

## 記録と再生（実装済み・使い方）

```
npm run replay -- --p1 earth --p2 sky --seed 42          # 1試合を記録して行動ログを出す
npm run replay -- --p1 earth --p2 sky --seed 42 --out tmp/g.json
npm run replay -- --in tmp/g.json                        # 保存した記録を再生
npm run replay -- --in tmp/g.json --log all --choices    # 効果の内部と選択も出す
npm run simulate -- --save tmp/records                   # 落ちた試合の記録を保存
```

- **1試合のシードは (基準シード, 神の組み合わせ, 何戦目) から決まる。**
  `--games` を変えても同じ組み合わせの同じ番号なら同じ試合になるので、
  200戦で落ちた試合を1000戦のときも同じシードで再現できる
- `simulate` はエラーごとに**再現コマンドをそのまま表示する**
- 再生は選択肢のラベルを毎回突き合わせているので、
  **エンジンの挙動を変えると古い記録の再生が失敗する**（＝退行の検出に使える）

## 優先度4: 遠隔対戦（実装済み・ここから先の残り）

**離れた2人がブラウザで対戦できる状態になっている。** 手順は `docs/deploy.md`。

```
npm run build && npm run serve    # 手元で2人 or AI と対戦
```

### 何をどう作ったか

- **対戦の実体は「選択の列」。** Vercel の関数は常駐せず呼び出しをまたいで何も覚えていないが、
  このエンジンは乱数が `GameState.rng` だけなので `(セットアップ, シード, 選択の列)` から
  盤面を完全に再現できる。保存物は `GameRecord` そのもので、`npm run replay` にもそのまま載る
- **止め方**: 記録が尽きたら `Chooser` が例外を投げる。スタックが畳まれて `resumeGame` まで戻り、
  `engine.state` は**その選択を求めた瞬間の盤面**のまま残る（`src/net/resume.ts`）
- **費用**: エンジンを回すのは `POST /api/game`（選択が入ったとき）だけ。
  ポーリングは `GET /api/v`（版番号1つ）で、**エンジンを import すらしていない**
  （`src/net/routes.test.ts` が構造として見張る）。実測は1試合まるごとで 0.2 秒（`src/net/cost.test.ts`）
- **隠された情報**は `src/engine/view.ts` が見せてよいものだけを積む（削らない）

### 残っている画面まわり

- **演出**（アニメーション）。ビューに `snap` 付きのログを載せてあるので、
  「前回からの差分」をタイムラインとして再生できる形にはなっている
- 観戦・チャット・持ち時間・アカウント・マッチメイキング（部屋コードだけ）
- カード画像（まだ存在しない）
- 画面定義書側の残り — ログイン / 新規登録 / デッキ編集 / マッチング
- **スマホの画面幅**（900px 以下でログを隠すところまでしかやっていない）

## 既知の不具合

### 解決済み

- ~~`weatherChanged` の bindings がプレースホルダ~~ → `Bound` に `{of:'weather'}` を追加して実際の天候を載せた。
  **ただし DSL から天候の束縛を読む手段はまだ無い**（`Condition` に「束縛した天候と比べる」枝が無い）。
  必要なカードが出た時点で足す。
- ~~威光の紋章の種族束縛が `let`~~ → `snapshot` に修正（継続的効果は効果ツリーより長く生きる）。
- ~~天候ダメージが「受けた本人が与えた」扱い~~ → 天候ダメージは `dealer` を持たないようにした。

### 残っているもの

- **ループ・ザ・ループが自分自身を手札に戻して無限ループする**（下記 3-0）
- **`RandomChooser` は不正な選択をしうる**（`chooseNumber` が山の番号に使われている場面で
  範囲外の数を返すなど）。実害は出ていないが、AIを賢くするときに整理する
- **`simulate` の「効果」勝因**（2.9%）は `{t:'win'}` を直接持つカード由来。
  どのカードかまでは記録していない
- **投了は記録に残らない**。`RoomService` が記録の外側で結果を決めている
  （エンジンの `surrender` と同じ結果になるが、`replayGame` では再現されない）

## 保留が確定している設計（蒸し返さない）

- **待機値・優先度は保留。** 型に `wait` / `priority` を optional で残し、
