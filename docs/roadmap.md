### 勝利条件は「届かない」のか「踏んでいない」のか

達成率と、達成できなかった試合も含めた**到達度**（`cond` を盤面で評価した0〜1）を並べる。

| 条件 | 達成率(乱→目) | 到達度の平均(目) | 読み |
|---|---|---|---|
| 十連撃の誓約 | 9.5% → 27.5% | 92% | 自傷を数えなくなって適正化（狙えば決まる） |
| 万象の軍勢 | 0.0% → 1.0% | 42% | **届かなくなった**。生命のパッシブを1種2体にしたため（4種×5体が遠い）。要調整 |
| 叡智の飽和 | 0.2% → 10.2% | 90% | 決まるようになった |
| 連鎖する空 | 10.3% → 4.5% | 18% | 相手依存（上記） |
| 完全なる水位 | 0.3% → 1.2% | 31% | ライフをちょうど35に合わせる手段が乏しい |
| 完全武装の証明 | 0% → 0% | 44% | **あと一歩**。装備5種を1試合で揃えきれない |
| 一撃必殺 | 0% → 0% | 測れない | 8点の一撃が出ない。**条件値の見直しが要るかもしれない** |
| 生命の氾濫 / 生死の振幅 | 0% → 0% | 31% / 19% | 99ライフ・50回変動とも**試合が短すぎて届かない** |
| 天象二十変 | 0% → 0% | 28% | 20回は多すぎる |

到達度は**デッキの組み方でも動く**（詠唱を厚くすれば詠唱の極致は伸びる）。
数値を変える前に、まず `decks/sea.txt` を詠唱寄りに振って測り直すのが安い。

## 優先度2: 打ち手をもう1段上げる — **実装済み**（2026-09-06）

海の打ち手が「打てるのにパスする」報告をきっかけに、評価の作りを入れ替えた。

**入れたもの**

1. **試し打ちを「積んだ時点」と「解決後」の両方で測る**（A案）。
   詠唱のように**スタック上でしか成立しない条件**は、そのカードだけを即解決する測り方だと
   消えてしまい 0点になっていた。勝利条件の進捗は2時点の**良い方**を採る
   （条件は成立した瞬間に誘発するので、どちらかで満たせば勝てる）
2. **解決フェイズをそのまま回してから測る**（ロールアウト）。
   相手のスタック項目も解決されるので、「いま解決したらどうなるか」で比較できる
3. **パスを候補の1つとして同じ手順で評価する。**
   固定しきい値との比較をやめ、「何も打たずに解決したら」を実際に回して基準線にした。
   **同点ならプレイする**（パスはそのフェイズ中ずっとパスになる不可逆な選択なので）
4. **相手の公開済み勝利条件の進捗を引く**（妨害の評価、`opponentWeight` 既定15）

**測った結果**

```
目的志向AI vs ランダム（600戦・先後入れ替え）   50.2% → 63.2%
新しい評価 vs 変更前の評価（AI同士192戦）              61.5%
「打てるのにパス」  大地 56→41 / 生命 74→37 / 海 83→79（30試合あたり）
実行時間            npm run simulate -- --games 600 --compare で約2分30秒
```

**効かなかったもの（測って捨てた）**

- 「同点より少し損でも打つ」（`passThreshold` を負に）… 51.6%。強くならない
- 伏せ札の重みを下げる（0.5→0.25 / 0.1）… 50%。海はむしろ弱くなる
- 妨害の重みを倍に（15→30）… 48.4%。いまの勝利条件では相手の進捗が1手で動かない

### 追試（2026-09-06 その2）: 案3を入れ、案2は見送り

リプレイで「ドレッドフル・タイダルウェイブを最後に打っていて、狙いどおりに回っていない」と報告があり、
2つ実装して測った。

- **案3「スタックに置くこと自体の価値」= 採用**（既定 `onStackWeight: 1`）。
  `active:'onStack'` の能力（詠唱の閾値・常在）を持つカードを置いたときに加点する。
  **カード名ではなく DSL の形で判定する**ので、AI に個別カードの知識は入らない
- **案2「スタックフェイズの続きまで回すロールアウト」= 実装したが既定にしない**（`rollout:'phase'`）。
  測ったら**どの形でも弱くなった**

海の火力デッキ20試合での実測（ドレッドを置いたあと押し上げ札が続いた割合＝狙いどおり打てた率）:

| 設定 | 勝率（AI同士・変更前比） | ドレッドを置いた回数 | 押し上げ率 | 1試合の与ダメ |
|---|---|---|---|---|
| **案3（採用）** | 52.8% / 49.3% | **25** | **56%** | **23** |
| 変更前 | — | 4 | 50% | 17 |
| 案2 自分だけ4手 | 39.6% / 41.7% | 27 | 15% | 17 |
| 案2 自分だけ2手 | 49.3% / 45.8% | 25 | 36% | 17 |
| 案2 両者4手 | 45.1% / 47.2% | 24 | 33% | 24 |

**案2が効かない理由**（見立て）: 続きを埋める打ち手が雑（打てるなら手札の先頭）なので、
候補ごとに違う「ありもしない続き」で採点してしまう。深くしても中の打ち手が悪ければ精度は上がらない。
直すなら続きも1手評価で選ばせることになるが、試し打ちの回数が桁で増えるので、
やるなら**明示指定の重いモード**として。コードは `rollout:'phase'` で残してある。

**まだ残っていること**

- **海のパスは半分しか減っていない。** 残りは「叡智の飽和（手札ちょうど15）」の引力で、
  カードを1枚使うと進捗が下がるため**プレイが本当にマイナス点**になる。
  1手先の評価では正しい判断で、直すには**複数サイクルを見る探索**が要る
- 相手の手札・伏せ札を読む要素は無い（見えないものは見ない、で通している）

## 優先度3: 残っている仕様の穴

いずれも企画側の判断が要るもの。**実装は判断が出てから。**

### 3-0. ループ・ザ・ループの無限ループ — **解決済み**（2026-09-06・B案）

「あなたの手札に等しい枚数まで、スタックからあなたのカードを手札に戻す。
これにより手札に戻したカードの枚数に等しいライフを回復する」＋**瞬発**。

解決中もカードはスタック上にあるので**自分自身を手札に戻せて**、
手札の枚数が減らないまま打ち直せた。1回ごとにライフが回復するので打ち手は延々と繰り返し、
600戦中4戦がスタックフェイズを抜けられなくなっていた。

**同じ穴は「熟達した跳躍」にもあった**（モード「スタック上のあなたのカードを1枚手札に戻す」）。
5回連続で「自分を戻して打ち直す」が通ることを確認済み。
違いは**得があるかどうかだけ**で、熟達した跳躍は繰り返しても何も起きないので誰も繰り返さなかった。

**B案で閉じた**（企画側判断）:

> **解決中の項目はスタックから出せない。**

`src/engine/select.ts` の `resolveStack` に `excludeResolving` を足し、
スタックから出す効果（`moveStackToZone` / `counterStack`）がこれを立てる。
選択肢の段階で外すので「選んだのに何も起きない」にはならず、
`{t:'all'}` のように選択を伴わない指定で外れた場合はログに出す（黙って減らさない）。

- 既存の「解決中の項目を再び解決しない」（`engine.resolving`）と同じ仕組みに乗せた
- **打ち消しも間に合わない**（解決に入ったカードは `counterStack` の対象にならない）
- 別のカードを戻す働きは残っている（テストで確認）
- 副作用として「自分をバウンスする」意図のカードは今後書けない

テストは `engine.test.ts` の「解決中の項目はスタックから出せない」3件。

ここに足せば、絞り込みボタンと既定表示の両方に反映される

```
npm run dashboard                 # tmp/dashboard.html（テスト・煙テスト・自動対戦・リプレイ）
npm run dashboard -- --quick      # 自動対戦を減らして速く
npm run dashboard -- --fragment   # Artifact 公開用（<html> の枠なし）
```

テスト結果は実際に `node --test` と `sweep` を走らせて集め、自動対戦はその場で回す。
**リプレイはブラウザ上で1手ずつ送れる**（フェイズ・プレイ・解決などの種類で絞り込み、
ライフの推移と手札・スタック・天候をその時点の値で表示）。

## デッキ構築（手組み）

デッキは `decks/*.txt` に人が書く。書式はカード名指定のテキスト。

```
# 大地 / アグロ            ← 行頭 # はコメント。狙いを書いておく
god: earth                 ← 必須
objectives: 十連撃の誓約, 完全武装の証明, 一撃必殺   ← 省略するとその神の全条件
3 紅蓮着火                 ← 「枚数 カード名」。枚数省略で1枚
```

```
npm run deck                      # decks/ を全部検証
npm run deck -- decks/earth.txt   # 1つを詳しく（勝利条件・タイプ内訳・内訳）
npm run deck -- decks/earth.txt --text   # 各カードの印刷テキストも
npm run builder                   # ブラウザで組む（tmp/deckbuilder.html）
npm run builder -- --fragment     # Artifact 公開用
```

### デッキビルダー（ブラウザ）

カードのテキストを見ながら枚数を調整し、その場で検証して `decks/*.txt` に貼れるテキストを出す。
**リポジトリを持っていない人（企画側）でも Artifact のURLだけで触れる。**

- 左に神ごとのカードプール（名前・テキスト・タイプで検索、タイプで絞り込み、`＋`/`−` で枚数）
- 中央にデッキ（枚数ゲージ・勝利条件の選択）、右に検証と内訳（タイプ別・キーワード・プレイ制限つき枚数）
- 下にデッキリストのテキスト（コピー）と、貼り付けて読み込む欄。`decks/` の4デッキは同梱してある
- **合否の判定はエンジンと同じパーサ**（`decklist.ts`）を esbuild で束ねて画面から呼んでいる。
  画面で通れば `npm run deck` も必ず通る（別々に数え直すとズレるため、そこは共有した）

- **カード名で書く。** 92枚すべて名前が重複しておらず、`validateDeck` の「同名3枚まで」も
  名前で数えているので数え方が一致する。名前が違えば**行番号と候補**を出して落ちる
- 検査は 30〜40枚 / 同名3枚 / 神の一致 の3つ（企画書「基本ルール」）＋勝利条件の神と件数
- `npm run simulate` / `npm run play` / `npm run dashboard` はすべてこのデッキを使う。
  `--decks <dir>` で別のディレクトリに切り替えられる（案を並べて比較するとき）
- **初期の4デッキはエンジン側で組んだ叩き台**。バランスの数字はこの構成に強く依存するので、
  企画側で組み直したら数字も取り直す

## 対話プレイ

```
npm run play                                     # あなた(P1) vs 目的志向AI(P2)
npm run play -- --deck1 decks/sea.txt --deck2 decks/life.txt
npm run play -- --you both                       # 2人で交互（ホットシート）
npm run play -- --you none                       # AI同士を眺める
npm run play -- --seed 42 --record tmp/game.json # 記録して後で再生
```

選択のたびに「前回から起きたこと」「盤面」「手札（印刷テキストつき）」が出る。
`b` 盤面 / `l` ログ / `q` 投了 / `?` ヘルプ。**相手の手札の中身と伏せた勝利条件は見えない。**

人が打った試合も `RecordingChooser` を通るので、そのまま `npm run replay -- --in` で
再生でき、ダッシュボードのリプレイにも載せられる。

## 記録と再生（実装済み・使い方）

```
npm run replay -- --p1 earth --p2 sky --seed 42          # 1試合を記録して行動ログを出す
npm run replay -- --p1 earth --p2 sky --seed 42 --out tmp/g.json
npm run replay -- --in tmp/g.json                        # 保存した記録を再生
npm run replay -- --in tmp/g.json --log all --choices    # 効果の内部と選択も出す
npm run simulate -- --save tmp/records                   # 落ちた試合の記録を保存
```

- **1試合のシードは (基準シード, 神の組み合わせ, 何戦目) から決まる。**
  `--games` を変えても同じ組み合わせの同じ番号なら同じ試合になるので、
  200戦で落ちた試合を1000戦のときも同じシードで再現できる
- `simulate` はエラーごとに**再現コマンドをそのまま表示する**
- 再生は選択肢のラベルを毎回突き合わせているので、
  **エンジンの挙動を変えると古い記録の再生が失敗する**（＝退行の検出に使える）

## 優先度4: 遠隔対戦（実装済み・ここから先の残り）

**離れた2人がブラウザで対戦できる状態になっている。** 手順は `docs/deploy.md`。

```
npm run build && npm run serve    # 手元で2人 or AI と対戦
```

### 何をどう作ったか

- **対戦の実体は「選択の列」。** Vercel の関数は常駐せず呼び出しをまたいで何も覚えていないが、
  このエンジンは乱数が `GameState.rng` だけなので `(セットアップ, シード, 選択の列)` から
  盤面を完全に再現できる。保存物は `GameRecord` そのもので、`npm run replay` にもそのまま載る
- **止め方**: 記録が尽きたら `Chooser` が例外を投げる。スタックが畳まれて `resumeGame` まで戻り、
  `engine.state` は**その選択を求めた瞬間の盤面**のまま残る（`src/net/resume.ts`）
- **費用**: エンジンを回すのは `POST /api/game`（選択が入ったとき）だけ。
  ポーリングは `GET /api/v`（版番号1つ）で、**エンジンを import すらしていない**
  （`src/net/routes.test.ts` が構造として見張る）。実測は1試合まるごとで 0.2 秒（`src/net/cost.test.ts`）
- **隠された情報**は `src/engine/view.ts` が見せてよいものだけを積む（削らない）

### 残っている画面まわり

- **演出**（アニメーション）。ビューに `snap` 付きのログを載せてあるので、
  「前回からの差分」をタイムラインとして再生できる形にはなっている
- 観戦・チャット・持ち時間・アカウント・マッチメイキング（部屋コードだけ）
- カード画像（まだ存在しない）
- 画面定義書側の残り — ログイン / 新規登録 / デッキ編集 / マッチング
- **スマホの画面幅**（900px 以下でログを隠すところまでしかやっていない）

- **海のAIのパスは半分だけ残っている**（2026-09-06 のテストプレイで報告 → 優先度2で対処）。

## 保留が確定している設計（蒸し返さない）

- **待機値・優先度は保留。** 型に `wait` / `priority` を optional で残し、
  「上から解決」一本で実装する。テストプレイで「打ち得」が問題化したときに導入する。
  順番確定フェイズ自体は雷雲・騙し討ちのフックとして残す（実装済み）
- **ミニオンは個体を持たず「種族 → 体数」だけ。** 個体ごとに状態が乗る効果は今後も作れない
- **マリガンなし。** プレイで問題が出たら企画書の案を試す
- **カードテキストは自動生成しない**（設計書 §8）
- **同神対決はルール上起こらない**（企画側確定 2026-09-02）。
  したがって「先行度が両者で並ぶ」のはデータの誤りであり、`determineFirst` の `RuleError` は
  そのまま残す。`tools/simulate.ts` も同神の組み合わせを作らない
- **騙し討ちの仕様は現状で正しい**（企画側確定 2026-09-02）。
  瞬発を持ちながら `timing:['orderPhase']` を明示しているカードは、
  カード側の指定がルールの既定（瞬発はスタックフェイズのみ）に優先する
