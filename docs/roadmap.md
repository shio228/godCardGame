## 優先度1: 1試合を通すループ

**これが今いちばん効く。** `flow.ts` に `play` / `resolvePhase` / `startCycle` /
`endTurn` / `endCycle` と部品は揃っているのに、**それを繋いで1ゲームを最後まで
回すものが存在しない**。

ルールエンジンを先に書いた目的は「AutoChooserで数千戦回してバランスを数字で決める」
ことだったので、今はその1歩手前で止まっている。特に**「4サイクル決着は意図した強制終了」
という確定済みの設計判断が、ドローフェイズが無いために一度も検証されていない**。

### 1-1. `startGame()`

ゲーム開始処理をまとめる入口が無い。

- デッキ構築の検証（30〜40枚 / 同名3枚まで）
- シャッフル（`shufflePile` は実装済み）
- 初期手札7枚
- `setupObjectives` の呼び出し

マリガンは企画側で「なし」確定なので不要。

### 1-2. ②ドローフェイズ

**丸ごと無い。** サイクル別ドロー枚数がコード上のどこにも存在しない。

| サイクル | 枚数 | 累計 |
|---|---|---|
| 0 | 7（初期手札） | 7 |
| 1 | 5 | 12 |
| 2 | 6 | 18 |
| 3 | 7 | 25 |
| 4 | 5 | 30（引き切り） |
| 5以降 | 1 | — |

ドローは先攻から行う。`startCycle` は現在 `revealPhase` → `cycleStart` 誘発で
終わっているので、その後ろに挿す。引き切りペナルティは `drawCards` に実装済みなので、
枚数さえ流せば4サイクル目の強制終了がそのまま動くはず（要検証）。

### 1-3. ③スタックフェイズ

`play()` は単発の関数で、フェイズのループが無い。

- 先攻から交互に「1枚プレイ」か「パス」
- パスを選んだプレイヤーはそのスタックフェイズ中パスしか行えない
- 手札0枚なら強制パス
- 両者パスでフェイズ終了
- 瞬発（`instant`）はこのフェイズでのみ使用できる → 1-5 と同時にやる

### 1-4. ④順番確定フェイズ

`phase: 'order'` と `orderPhaseStart` イベントの器はあるが、**実行する関数が無い**。
雷雲のランダム無効化・騙し討ち・創造のカードのフックとして残すと決めた場所。
中身は優先度2の天候実装と重なる。

### 1-5. 瞬発（`instant`）

キーワードは定義済みだが、`play()` に「瞬発なら即座に解決してスタックから降ろす」
経路が無い。スタックフェイズ限定の制約も未実装。
sweep は `onResolve` を手で叩いているので、**現在のテストではこの穴が見えない**。
1-3 を書くときに同時にやるのが自然。

### 1-6. 降伏

即敗北。軽い。

## 優先度2: 天候の能動効果

エンジンは天候を**条件として読む**ことはできる（`weatherIs` / `weatherSide`）。
雨・豪雨のサイクルボーナス無効（`NO_CYCLE_BONUS_WEATHER`）と `weatherImmune` も入っている。
しかし**天候が能動的に起こす処理が1つも無い**。

| 天候 | 起こすべき処理 | 現状 |
|---|---|---|
| 炎天 | プレイ時・解決時に1ダメージ（ダメボ非適用） | 無し |
| 豪雨 | プレイごとに手札1枚捨て | 無し |
| 吹雪 | ターン終了時に両者5ダメージ（ダメボ非適用） | 無し |
| 雷雲 | 順番確定フェイズにスタック各カードを1枚ランダム無効化 | `weatherNegate` イベントの器のみ |
| 終末 | ターン開始時に山札上から5枚除外 | `apocalypse` フラグと「終末中は天候変更不可」のみ |

### 設計判断: 天候定義テーブルから注入する

フェイズ処理にベタ書きする案もあるが、**天候ごとの定義テーブルを持ち、そこから
`ContinuousMod` / `GrantedTrigger` を state に注入する形**を採る。

理由:

- `weatherImmune` や「炎天のダメージを受けない」系のカードが、既存の `activeMods`
  経路にそのまま乗る。天候ダメージだけ別経路にすると、軽減・回避との相互作用を
  二重に書くことになる
- 天候を1つ増やすときにフェイズ処理を触らずに済む
- 「置換効果は必ず1本の経路を通る」という既存方針と一貫する

天候ダメージは `tags: ['weather']` を持つので、サイクルボーナス非適用は
`damage.ts` の既存分岐でそのまま効く。

### 順序の理由

優先度1より後、優先度3より先。**1が終わるまで天候を実装しても検証できず**、
逆に**終末が動かないとゲームが終わらず、吹雪と炎天が無いと決着サイクルの統計が
丸ごとズレる**ため、自動対戦より先に必要。

## 優先度3: 自動対戦ハーネス（`tools/simulate.ts`）

`tools/sweep.ts` の流儀で、`AutoChooser` 同士のランダム対戦をN戦回す。

出したい数字:

- 神ごとの勝率（対戦相手の神別のマトリクス）
- 平均決着サイクル（設計目標は3、長くて4）
- 特殊勝利ごとの達成率 — 達成率0%の条件と、逆に達成しやすすぎる条件を炙り出す
- **先攻・後攻の勝率差**

最後の1つが重要。「スタックは後にプレイした方が先に解決する」「パスは撤回できない」
という構造から**後攻の方が有利ではないか**という仮説があり、これが正しければ
「先行度が高い＝先攻」ではなく「先行度が高い＝先攻/後攻を選べる」に変えるべき
という話になる。ここで決着がつく。

**ここまで来るとプロジェクトの性質が変わる。** 今は「カード1枚が正しく解決するか」を
手で確かめる段階だが、以降は先行度の配分・特殊勝利の難易度・終末のタイミングを
すべてシミュレーションで決められる。

## 既知の不具合

### `weatherChanged` の bindings がプレースホルダ

`effects.ts` の `setWeather` が出すイベント:

```ts
bindings: { from: { of: 'number', value: 0 }, to: { of: 'number', value: 0 } }
```

**天候なのに `number` の 0 が入ったまま。** 今は `measure:'events'` で回数だけを
数えるカード（明鏡止水 / セレスティアル・ディザスター）しかないので誰も困っていないが、
「炎天に変わったとき」のような変更前後を参照するカードが1枚でも出た瞬間に嘘の値を返す。

根の原因は `Bound` に天候を表す枝が無いこと。対応は2択:

1. `Bound` に `{ of: 'weather'; value: Weather }` を足す
2. この2つの binding を消す（参照する手段が無いことを明示する）

**`as never` を排除した方針と同じで、「黙って0を返す経路」は残さない。**

## 保留が確定している設計（蒸し返さない）

- **待機値・優先度は保留。** 型に `wait` / `priority` を optional で残し、
  「上から解決」一本で実装する。テストプレイで「打ち得」が問題化したときに導入する。
  順番確定フェイズ自体は雷雲・騙し討ちのフックとして残す
- **ミニオンは個体を持たず「種族 → 体数」だけ。** 個体ごとに状態が乗る効果は今後も作れない
- **マリガンなし。** プレイで問題が出たら企画書の案を試す
- **カードテキストは自動生成しない**（設計書 §8）
