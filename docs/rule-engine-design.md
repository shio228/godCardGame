## 1. 出発点にある5つの厄介さ

企画書を効果表現の観点から読むと、このゲームには一般的なTCGにない構造が5つあります。設計はこの5つに引きずられます。

**① スタックに「カード」と「効果」と「アクション」が混在する**
「相手に5点…」を3回スタックに乗せる（アースレイジ）、引き切りペナルティの「あなたは30点のダメージを受ける」、攻撃指令・防御指令・レゾナンスをスタックに乗せる。しかもこれらは *スタックに乗るので対象に取れる*（打ち消し・軽減・並び替え）。
→ **スタック項目は card / effect / action を統一した器でなければならない。**

**② カードがスタック上で「生きている」**
常在、詠唱カウンター、上に乗せられたら誘発、一つ上／一つ下を参照、連続数を参照。MTGならスタック上の呪文はほぼ不活性ですが、このゲームはスタックが盤面です。
→ **StackItem は状態を持つ第一級オブジェクト。**

**③ 数値がほぼ全部「式」**
サイクルボーナス、詠唱カウンター、武器の装備数、ミニオンの数、連続しているカードの数、プレイヤーが選ぶ x。定数で済むカードの方が少数派です。
→ **数値は `number` ではなく `Value`（数式の木）。**

**④ プレイそのものに制約がかかる**
「1サイクルに1枚しかプレイできない」「ライフが相手より少なく手札2枚以下のとき」「手札を1枚捨てることでプレイできる」「サイクルの初めにプレイするカードでなければならない」「順番確定フェイズにプレイしてよい」——コストがない代わりに、制約がカード個性の主要な担い手になっています。
→ **`CardDef.play` を一級市民にする。** 効果とは別レイヤー。

**⑤ デッキもスタックも複数になりうる**
海「並列思考」でデッキが2分割され、創造「スタック分割」でスタックが増え、創造「ケイオス・フォーチュン」でデッキが共通化されます。
→ **`decks: Deck[]` / `stacks: Stack[]` を最初から前提にする。** 後付けだと全処理の改修になります。

## 2. 全体構造

```
CardPool
 ├ gods      : GodDef[]         … 神のパッシブ・使えるアクション／種族／トークン
 ├ cards     : CardDef[]        … 通常カード
 ├ tokens    : TokenDef[]       … 武器・防具・神器（場に出る）
 ├ minions   : MinionDef[]      … 種族ごとの能力
 ├ actions   : NamedActionDef[] … 戦技 / 攻撃指令 / 防御指令 / レゾナンス
 └ objectives: ObjectiveDef[]   … 公開特殊勝利条件

CardDef
 ├ 印刷情報（name / types / text / keywords / immovable …）
 ├ play: PlayRule               … 条件 / 追加コスト / 回数 / タイミング / 位置
 └ abilities: Ability[]
      ├ onPlay      … プレイした瞬間
      ├ onResolve   … 解決フェイズでの本体
      ├ triggered   … 「〜されたなら」
      ├ thresholds  … 閾値誘発の糖衣（「詠唱が3/6/9になったら」）
      ├ activated   … 「いつでも〜してもよい」
      └ continuous  … 数値・ルールを書き換え続ける（置換効果を含む）

Effect（効果の木）
 ├ 原子効果 : damage / draw / heal / discard / foresee / moveCards / shuffle / splitDeck /
 │            reorderStack / counterStack / moveStackItem / moveStackToZone / addToStack /
 │            resolveStack / redirect / addCounter / performAction /
 │            createToken / createMinion / sacrificeMinion /
 │            gainStatus / addPlayerCounter / setWeather / snapshot / win …
 ├ 制御構造 : seq / repeat / while / if / forEach / optional / modal / bind / let
 └ 逃げ道   : handler { id }

Value      : cycle / counters / playerCounter / countStack / countZone / countTokens /
             countMinions / consecutiveRun / countEvent / snapshotValue / countOf /
             chooseNumber / add,mul,min …
Selector   : PlayerSel / EntitySel / StackSel / CardSel / TokenSel / SpeciesRef
Condition  : cmp / weatherIs / weatherSide / matchesStack / matchesCard / and,or,not
```

判別子はすべて `t` に統一し、JSONへそのままシリアライズできる形を保っています。

## 3. 発見: 「戦技」「攻撃指令」「防御指令」「レゾナンス」は同じ仕組み

4神の設定シートを横断して読むと、同じ形の概念が独立に4つ出てきます。

| 神 | 名前 | 中身 |
|---|---|---|
| 大地 | 戦技（斬撃 / 刺突 / 打撃） | 3つから1つ選んで行う。カードから「2回行う」等で参照される |
| 生命 | 攻撃指令 / 防御指令 | カードが「スタックに乗せる」。それ自体が常在を持つこともある |
| 空 | レゾナンス | 天候で効果が丸ごと変わる。「行う」「スタックに乗せる」両方ある |

いずれも **①カード本体とは別に定義され ②複数のカードから参照され ③スタックにも乗る**。
これを `NamedActionDef` として第一級の概念にしました。カードごとに効果を複製する必要がなくなり、バランス調整も「斬撃を3点→4点」の一箇所で済みます。

```ts
{ t: 'performAction', times: 2, distinct: true,
  action: { t: 'chooseFrom', group: 'earth/combatArt' } }   // コンビネーション

{ t: 'addToStack', payload: { t: 'action', action: 'life/attackOrder' } }  // 創命：万物創生
```

**この構造は創造の神にも効いてきます。** 設定シートに「神ごとの特色（戦技、詠唱、レゾナンス、ミニオン）をコピーできるのか？」というメモがありますが、NamedAction として統一しておけば「相手の NamedAction グループを自分のものとして扱う」で表現できます。バラバラに実装していたら不可能でした。

## 4. 「常在」は実装上3つに分解される

企画書の定義は「常在：スタック上にある間＜＞内の効果が常に働く」ですが、実際のカードは**挙動が3種類混ざっています**。

| カード | テキスト | 実体 |
|---|---|---|
| アンプリファイバブルシールド | ＜詠唱カウンターに等しいダメージを軽減する＞ | **継続 continuous** |
| 不壊剛壁 / 根性 | ＜自傷ダメージを受けない＞＜ライフが0以下になるなら…＞ | **継続（置換効果）** |
| リアクティブアクアスフィア | ＜上に相手がカードを乗せた時、3ダメージ＞ | **誘発 triggered** |
| ドレッドフル | ＜詠唱が3になったら…＞ | **誘発 triggered** |
| 既知の危機 | ＜相手が乗せたとき、〜を行ってもよい＞ | **誘発（任意）triggered + optional** |
| 天水の祝福 | ＜豪雨なら豪雨の影響を受けない＞ | **継続（条件付き）** |

**決定: テキスト上の表記は「常在」1本のままとする。** 実装データのみ `Ability.kind` で分けます。
ただしUI上の課題は残ります——プレイヤーが自分で発動する能力（旧・既知の危機の起動型など）が今後増えた場合、「押せるカード」の見分けがつきません。現在の設定シート版の既知の危機は誘発型（optional）に変わっており、この問題は一旦回避されています。**能動的に押す常在をこれ以上増やさない**方針であれば、表記統一のままで問題ありません。

## 5. ダメージパイプライン（確定）

企画書に散らばっている修正要素を1本のパイプラインに整理しました。

```
 1. 基礎値            カードの amount を評価
 2. サイクルボーナス   + cycle
                      （ignoresCycleBonus / 雨・豪雨 / 天候ダメージ では加算しない）
 3. 与ダメ加算補正     攻勢+1、剣の斬撃+1、槌の打撃+3、魔獣のダメボ
                      (damageDelta direction:'dealt' / tags で絞る)
 4. 乗算補正          炎天で「炎」タイプ×2   (damageMultiplier)
 ─────── ここまでが「与えるダメージ」＝ 誘発や bind が参照する値 ───────
 5. 着弾先の差し替え   防御指令のミニオン割り振り、創造の対象変更 (damageRedirect)
 6. 被ダメ加算補正     攻勢+1               (damageDelta direction:'taken')
 7. 装甲              armor を減算（ignoreArmor なら飛ばす）
    ★ evasionInput = この時点の値を退避
 8. 軽減              reduction / damageReduction を減算（unreducible なら飛ばす）
 9. 回避判定          evasionInput ≤ evasion なら 0 にする（unavoidable なら飛ばす）
10. シールド          shield から優先消費
11. ライフ減算
```

企画書の「倍率はダメージボーナスが適用されたのちに反映される」を 2→4 の順で反映しています。

**回避判定に渡すのは「軽減前」の値**である点が要点です（★）。軽減後の小さくなった値で回避判定をすると、回避＋軽減の重ね掛けで完封が容易に成立してしまうためです。

> 例: 回避3 / 5ダメージ / 軽減3
> - この設計 → evasionInput=5、5 > 3 なので回避は働かず、軽減して **2ダメージ**
> - 軽減後に判定した場合 → 2 ≤ 3 で **0ダメージ**（完封）

**ダメージタグ**（`slash` `thrust` `strike` `attackOrder` `fire` `weather` `self` `system`）が修正の絞り込みに使われます。「あなたの与える斬撃のダメージは+1」「自傷ダメージを受けない」「炎天によるダメージを受けなくなる」は全部タグで書けます。

**軽減量の参照**: アンプリファイバブルシールドの「軽減する度、詠唱カウンターをダメージ分取り除く」のように、置換効果の内部で「実際に軽減した量」が必要になります。`damageReduction.onApply` の実行時に `reduced` を暗黙束縛する規約にしています。

置換効果（ドロー枚数、ライフ0の肩代わり、天候変更の打ち消し）も同じ思想で、**その操作を実行する経路が必ず置換層を通る**設計にします。直接 `hand.push(deck.pop())` を書ける場所を作らないのが肝心です。

## 6. DSL拡張（宿題はすべて反映済み）

27枚を書いた時点で表現力が足りなかった5点は、DSLに入れました。

| # | 問題 | 入れたもの | 使用カード |
|---|---|---|---|
| 1 | 「3枚探して1枚ずつ3か所へ」— 選んだ集合を一旦置く場所がない | 一時領域 `Zone: 'staging'` + `moveCards.position` | 未来の選択 / デジャヴ |
| 2 | 「**このカードが**与えたダメージ」— 発生源単位の集計 | `countEvent.source` | リアクティブアクアスフィア |
| 3 | 「瞬発を**選ぶなら**手札を捨てる」— 選択後に決まるコスト | `let` + `Condition.matchesStack` | 既知の危機 |
| 4 | 「**このカードによって生成した**武器」— トークンの出自 | `createToken.mark` + `TokenFilter.mark` | インスタントフォージ |
| 5 | 「**選んだ種類とは違う**種類」— 選択結果の束縛 | `let` + `Selection`（stack/card/token/species/entity/player/number） | 再生産 |

### 中核になったのは `bind` と `let` の分離

3・5 は同じ根から来ていました。**「直前の何かを指し示す」手段が数値しかなかった**のが原因です。これを2つに分けました。

```ts
// bind: 効果を実行し、その結果を束縛する
{ t:'bind', name:'dealt', of:{ t:'damage', … }, then: … }   // dealt = 与えたダメージ量
{ t:'bind', name:'returned', of:{ t:'moveStackToZone', … }, then: … }  // returned = 戻した集合

// let: 「選ぶ」だけ行い、結果を束縛する（何も起きない）
{ t:'let', name:'chosen', select:{ of:'stack', sel:{ t:'choose', … } }, then: … }
{ t:'let', name:'sacrificed', select:{ of:'species', sel:{ t:'choose', … } }, then: … }
```

束縛名は各セレクタの `{t:'var', name}` で読み出します。数値として読むときは `{t:'var'}`（数値束縛）か
`{t:'countOf', name}`（集合の要素数）。ループ・ザ・ループの「手札に戻した枚数に等しいライフを回復」が後者です。

### 空のカードを書いて追加したもの

空14枚を書く過程で、さらに4つ足りませんでした。いずれも小さい追加です。

- `while`（支払いつきの任意反復）— サンダーテンペストの「カードを1枚捨てるたび、これを繰り返してもよい」。固定回数の `repeat` とは別物。
- `countEvent.weather` — 明鏡止水の「凪に変わるのが5回目以降なら」。空の特殊勝利「累計20回天候が変わった」も同じ仕組みで書けます。
- `grantTrigger.onceOnly` — ウェザートランジションの「この効果は1サイクルに1つしかつかない」。
- `gainStatus.capFromThisSource` — エクストリームベロシティの「このカードで得られる回避の上限は6」。**全体の上限ではなく発生源ごとの累積上限**である点に注意が要ります。

### 残っていた3点も実装済み

**① `StackFilter.not` / `CardFilter.not` / `TokenFilter.not`**
ウィンドインタラプトの「『ウィンドインタラプト』と名の付くカード**以外**」がデータで書けるようになりました。フィルタは再帰的なので `not: { not: {...} }` も成立します。

**② 誘発の粒度を「1回の効果につき1回」に確定**

これは `drawn` 1つの問題ではなく、誘発全体の規約でした。既定を `perEvent`（1回の効果につき1回発火）とし、1枚／1体ごとに発火させたいときだけ `granularity: 'perUnit'` を明示します。

スウィフトマニューバーの「カードを引く度に回避1」＋設定シートの「複数枚引いても1」が、これで既定のまま成立します。逆に「引いた枚数」が欲しい場合は、後述の暗黙束縛 `count` で取ります。

**③ `thresholds`（閾値誘発の糖衣）**

```ts
{ kind: 'thresholds', active: 'onStack', counter: 'chant',
  steps: [
    { at: 3, effect: { t:'damage', …, amount: 2 } },
    { at: 6, effect: { t:'damage', …, amount: 5 } },
    { at: 9, effect: { t:'damage', …, amount: 13, flags:{ unreducible: true } } },
  ] }
```

`triggered`（counterChanged + `cmp '=='`）を steps の数だけ並べたものと**完全に等価**です。挙動は変えていませんが、ドレッドフルの3段階が一望できるようになり、バランス調整のとき閾値と火力の対応を見誤りにくくなります。

### 生命22枚を書いて追加したもの

生命は設定シートの22枚すべてをデータ化しました。**handler はゼロ**でしたが、10個の追加が必要でした。ミニオンという新しい盤面要素が入るぶん、当然ではあります。

| 追加 | きっかけ |
|---|---|
| `SpeciesFilter`（`is` / `not`） | 「**死霊以外**のミニオン」が3枚に登場。種族の否定は頻出形 |
| `countSpeciesKinds` | ライフリコール「死亡した死霊以外のミニオン**1種類につき**1枚」 |
| `damage.species` | 栄光の凱旋「攻撃指令により**人で**ダメージを与えたとき」 |
| `granularity: 'perSpecies'` | 奥義枠「ミニオンが**1種類**死亡するか生成されるたび」 |
| `TriggerEvent.on` を配列可に | 同上「死亡する**か**生成される」 |
| `StackFilter.actionId` | 奇襲作戦「**攻撃指令が**対象に取られなくなり」 |
| `grantContinuous.cond` | 吹雪身代わり「死霊以外が3体以上**いるなら**無効にする」 |
| `ContinuousMod.replaceEvent` | 雷光顕現「無効化が行われるなら、**代わりに**ミニオン1体を生贄にしてもよい」 |
| `snapshot.select` | 最期の献身・加護の紋章（後述） |
| `GodDef` | 神のパッシブに置き場がなかった（後述） |

#### 発見1: 「1種類につき」は体数ではなく種類数

ライフリコールの「死亡した死霊以外のミニオン**1種類につき**1枚」を `countMinions`（体数）で書くと、カードパワーが4倍近く変わります。名前を `countSpeciesKinds` と明確に分けました。ミニオンが「種族ごとの数」で管理される以上、**「数」と「種類数」の取り違えは今後も起きうる事故**なので、型で分けておく価値があります。

#### 発見2: `snapshot` が「ability をまたぐ束縛」を担う

最期の献身は「**スタックに乗せたとき**ミニオン1種類を選ぶ」→「**解決時に**その種類が死んだ数だけ回復する」という構造です。選択が onPlay、参照が onResolve なので、`let` では届きません（`let` はひとつの効果ツリー内で閉じる）。

海の抱擁のために作った `snapshot`（ライフを記録して後で照合する）を、値だけでなく**選択結果も記録できる**よう拡張しました。これで3つの時間スケールが揃います。

| 構文 | 生存範囲 |
|---|---|
| `let` | ひとつの効果ツリーの中だけ |
| 暗黙束縛 | ひとつの誘発の実行中だけ |
| `snapshot` | **そのスタック項目が存在する間ずっと**（ability をまたぐ） |

加護の紋章も同じ形です（onPlay で種族を選び、continuous がそれを参照し続ける）。

#### 発見3: 神のパッシブに置き場がなかった

生命の「ターン開始時ドロー前に全種2体生成」を書こうとして気づきました。**カードにもトークンにもミニオンにも属さない、神そのものの常時能力**の受け皿がありません。大地の「攻勢」「難攻不落」、海の予知領域も同じ立場です。

`GodDef` を足して、パッシブ・使える NamedAction・使える種族・生成できるトークンをまとめました。デッキ構築時のバリデーション（大地のカードに海の装備は入らない）にもそのまま使えます。

**ただしここで1つ、エンジン側の課題が残りました。** 生命のパッシブは「ターン開始時**ドロー前**に」生成します。現在の `cycleStart` 誘発には、同じフェイズ内での順序を指定する手段がありません。企画書のフェイズ定義（①サイクル開始 ②ドロー ③スタック…）に照らすと、これは①の中の話なので `cycleStart` で正しいのですが、**同じフェイズに複数の誘発が乗ったときの順序**は解決エンジンの設計で決める必要があります。

### 残り29枚を書いて追加したもの（＝DSLの収束）

海・大地・空の残り29枚（海7・大地14・空8）とトークン1を書き足して、設定シート掲載の全カードをデータ化しました。**この29枚で必要になった型の追加は2つだけ**です。

- `CardFilter.is` — ブレイジングラッシュ「**それらの**カードを墓地に置く」
- `EventKind: 'bounced'` — レゾナンスリージョン「このカードが**バウンスされたとき**」

前の29枚（生命22＋空の追補）が10個の追加を要求したのに対し、この29枚は2個で済みました。**DSLが収束した**と判断してよい数字だと考えています。

既存の構文が期待どおり効いた例:

| カード | 使った構文 |
|---|---|
| ランページチェイン / ファイナルアタック | `bind` が `performAction` の結果（そのアクションの合計ダメージ）を受け取る |
| 燃え盛る大地 | 暗黙束縛 `source` → `controllerOf` で「そのコントローラー」を引く |
| テラブレイズ・リビルド | `let` を2段重ねて装備と手札の両方を束縛し、`countOf` で合計枚数を出す |
| クルーエルカーネイジ | `alternativePlay`（「プレイする代わりに」はプレイ制約層の話なので継続効果として与える） |
| 気炎万丈 / 自在の神翼 | `damageDelta.amount` に `{t:'cycle'}` を入れて「天候ダメージにダメボを乗せる」 |
| レイジングスカイ | `replaceEvent` の `with` 省略＝「単に打ち消す」。雷光顕現（代わりに生贄）と同じ構文 |

#### 追加しなかったもの — 天焦灼火

「天候が【炎天】である場合に限り、ダメージボーナスが適用される」は、`DamageFlags` に条件式を持たせれば1行で書けます。が、**この1枚のためにフラグを条件式にすると、以後すべてのダメージ計算が条件評価を通る**ことになります。`if`/`else` で同じ `damage` を2回書く冗長さを受け入れました。§7 の基準②（使用カードが1〜2枚なら拡張の元が取れない）を、handler ではなく「DSL拡張の見送り」に適用した形です。

#### 実装時に注意が要る点

- **レゾナンスの評価タイミング**: リーサリティブリザードは「4点 → レゾナンス → 天候を吹雪に変更」の順です。レゾナンスは現在の天候で分岐するので、**天候変更の前か後かで結果が丸ごと変わります**。テキストの順序どおり前に置いていますが、意図どおりか確認の価値があります。
- **順番確定フェイズを使うカードは騙し討ち1枚だけ**です（他は雷雲）。`PlayRule.timing` はこの1枚のために存在しています。フェイズごと削るなら、このカードの再設計とセットになります。

### `countEvent` の measure — 「回数」か「数量」かは必ず明示する

`countEvent` には**イベント種別ごとに暗黙のルールを持たせません**。`measure` を必須フィールドにして、式の側に書かせます。

```ts
{ t:'countEvent', event:'weatherChanged', scope:'game', measure:'events', weather:'calm' }
  // 明鏡止水「凪に変わるのが5回目以降なら」= 発生回数

{ t:'countEvent', event:'minionDied', scope:'cycle', measure:'units', species:{ not:'wraith' } }
  // 犠牲の残り香「死亡した死霊以外のミニオンに等しい数」= 体数
```

| measure | 意味 |
|---|---|
| `'events'` | イベントの発生回数。1イベント = 1 |
| `'units'` | イベントが伴った数量の合計（枚数・体数・ダメージ量） |

**なぜ既定値を置かずに必須にしたか。** 「minionDied だけ体数を加算」のようにイベント種別ごとに意味を変えると、`countEvent` を読んだだけでは何を数えているか分からなくなります。これは**ライフリコールのときに避けた落とし穴と同じもの**です（体数の `countMinions` と種類数の `countSpeciesKinds` を名前で分けた判断）。同じ規律をここにも通しました。

現在の7箇所の内訳:

| カード | event | measure | 理由 |
|---|---|---|---|
| リアクティブアクアスフィア | damageDealt | `units` | 「ダメージを与えていたなら」＝通った合計が1以上か。`events` だと0ダメージのイベントも1と数える |
| 栄光の凱旋 | damageDealt | `units` | 同上 |
| 犠牲の残り香 | minionDied | `units` | 「死亡した数に等しい数」＝体数 |
| 最期の献身 | minionDied | `units` | 「死亡した数と同じだけ」＝体数 |
| 明鏡止水 | weatherChanged | `events` | 「5回目以降なら」＝回数 |
| セレスティアルディザスター | weatherChanged | `events` | 「変化していたなら」＝回数 |
| フローレスフェザー | damageTaken | `units` | 「ダメージを受けていないなら」＝受けた合計が0か（完全軽減されたなら受けていない） |

`drawn` を `countEvent` で使うカードは**現時点で1枚もありません**。必要になった時点で、そのカードのテキストから measure を決めます。

> **副産物**: `measure` を必須にしたことで7箇所すべてが型エラーとして浮上し、そのうち1箇所（犠牲の残り香）に `as never` キャストが残っていて存在しないフィールド名（`of`）の誤りを隠していたことが判明しました。キャストは除去済みで、ファイル内に `as any` / `as never` / `@ts-` は0件です。

### 暗黙束縛の契約

粒度を perEvent に決めた結果、**「その効果で何枚引いたか / 何体死んだか / 何点通ったか」を誘発側から取る手段**が必要になりました。毎回 `bind` を書かせるのは冗長なので、イベント種別ごとに固定名を予約し、エンジンが誘発の実行直前に束縛する規約にしています。

| イベント | 暗黙束縛 |
|---|---|
| played / placedOnStack / resolved / resolving / countered / reordered | `source` |
| counterChanged | `source` / `count`（変化後の値）/ `delta` |
| damageDealt / damageTaken | `source` / `amount`（実際に通った値）/ `target` |
| drawn / discarded / foreseen | `count` / `cards` |
| minionCreated / minionDied | `species` / `count` |
| tokenCreated | `token` |
| weatherChanged | `from` / `to` |
| lifeChanged | `delta` |

継続的効果にも同じ規約があります（`damageReduction.onApply` → `reduced` = 実際に軽減した量）。

死霊の「減った数をxとして相手にxダメージ」は、これで `{ t:'var', name:'count' }` と書けます。以前はカード側で `diedCount` という場当たりの名前を使っていました。

## 7. handler に逃がす基準

ハイブリッド方式の生死を分けるのは「どこで諦めるか」の基準です。

**handler に逃がしてよい**
1. ゲームの基礎構造そのものを書き換える（並列思考＝デッキ分割、スタック分割、デッキ共通化、ルール無視、テキスト書き換え）
2. その概念を使うカードが 1〜2 枚に留まり、DSL 拡張の元が取れない
3. DSL に入れると、そのカードと無関係な全カード・全処理に概念が漏れる

**逃がしてはいけない（DSLに昇格させる）**
- 3枚以上のカードで再利用しそうな概念（天候操作、予知、カウンタ、スタック並び替え、戦技、ミニオン、装備は全部DSL側）
- 数値のバランス調整対象になるもの
- AIやログ解析が中身を読む必要があるもの

**実測**: 92枚中 handler 行きは4枚（4%）。内訳は海の並列思考1枚と、創造の3枚です。
**大地22枚・空22枚・生命22枚は handler ゼロ**で全部データ化できました。

**確定: 創造の神は「handlerの神」として扱う。**
設定シートの案はほぼ全てが「ルールを書き換える」「テキストを書き換える」「構造を変える」内容で、他神と同じ比率でDSL化するのは原理的に無理です。創造だけ handler 比率が高いことを許容し、**その代わりカード枚数を他神より少数精鋭にする**という整理にします。

創造の中でも DSL で書けるものは書きます（デジャヴは staging を使って完全にデータ化できました）。handler 行きにする判断はカード単位で、神単位ではありません。

創造の handler 3枚が、そのまま基準①②③の教科書例になっています。

| カード | 基準 | 理由 |
|---|---|---|
| スタック分割 | ① | スタックの数という基礎構造を変える |
| ケイオス・フォーチュン | ① | デッキの所有という基礎構造を変える |
| ジャストキル | ③ | 「何らかの数値を0にするなら」はエンジンの全数値操作の監視が要り、DSLに入れると全効果に概念が漏れる |

なお、①の2枚は **`GameState.stacks[]` / `decks[]` を最初から複数前提にしてある**ため、handler 側の実装は素直に書けます（§1⑤）。ここを単数で作っていたら、創造の実装時に全処理の改修が発生していました。

## 8. カードテキストは自動生成しない

handler の中身は日本語化できませんし、日本語の言い回し（「〜してもよい」「その後」「上限は3枚」）を DSL から自然に組み立てるのは DSL を歪ませる割に成果が出ません。

**方針**: `CardDef.text` に人間が書いたテキストを持ち、それを正とする。DSL はあくまで挙動の定義。
代わりに **DSL → テキストの整合性リンタ**を用意します（§9-5）。

## 9. テスト戦略

1. **型チェック**: `npm run typecheck`。`strict` + `exactOptionalPropertyTypes` で通ることを確認済み。
2. **ゴールデンテスト**: カード1枚ごとに「初期状態 → 効果適用 → 期待状態」を宣言的に書く。スタック操作系はここでしか担保できません。
3. **不変条件テスト**: ライフ・手札枚数・スタック枚数の保存則、無限ループ検出（空のコンボ、人間ミニオンの倍増が必ず引っかかる）。
4. **ランダム対戦（後段）**: 手なりAIで数千戦回し、平均決着サイクル数を計測。企画書の「3ターンで決着」が実際に成立するかの検証になります。獄焔15、詠唱15、天候5回など特殊勝利の到達率もここで出ます。
5. **テキスト整合チェック**: `text` に含まれる数字と DSL 内の定数の集合を突き合わせ、不一致を警告する簡易リンタ。

## 10. 決定事項

### ✅ 確定

**軽減 → 回避の順で適用する。ただし回避判定に渡すのは軽減前の値。**（§5）

**対象・スタック位置は解決時に評価する（プレイ時ロックしない）。**
副作用として、プレイ時点では最終的な着弾先が確定しないため、UI側で「解決時に決まる」表現を画面定義書に反映する必要があります。

**待機値・優先度は保留。型には `wait` / `priority` を optional で残す。**
「上から解決」一本で実装し、テストプレイで「打ち得」が問題化したときに導入します。順番確定フェイズ自体は、雷雲・騙し討ちのフックとして残ります。

**「常在」はテキスト表記を分けない。** 実装のみ3分解（§4）。

**スタック上に生成された「効果」に詠唱カウンターは乗らない。**
「詠唱を持つカードが存在するスタックに海の神の *カード* が置かれるたび」の対象はカードのみ。生成された効果を数えるとドレッドフルやスプリットディメンションが自己加速するループが生まれます。実装では `StackFilter.kind: 'card'` で絞ります。

**カードの一次資料は各神の設定シート。**「カード置き場」は古いため参照しない。

**創造の神は「handlerの神」として扱う。** handler 比率が高いことを許容し、その代わりカード枚数を他神より少数精鋭にする（§7）。

**5神すべてのカード案を現時点の設定シートで確定とする。** 設定シート掲載の全92枚をデータ化済み。

**ミニオンは「種族ごとの数」だけで管理する。**
個体IDも体力も攻撃力も持たず、盤面上の状態は `MinionPool`（種族 → 体数）だけです。「ミニオン1体を対象に取る」効果は存在せず、常に「種族」と「数」で指定します。設定シートの「ミニオン自体に体力、攻撃力の表現はなく、数のみが決まっている／人間という枠にダイスを置くなどして表現」に沿った形です。

この確定は実装をかなり軽くします。ダメージの割り振り（防御指令、天使の超過吸収）が「どの個体に何点」ではなく「種族プールから何体減らすか」の計算になり、UIも種族4枠のカウンタで済みます。
一方で、**個体ごとに状態が乗る効果は今後も作れません**（「このミニオンに+1/+1」「このミニオンは対象に取られない」は不可、「この種族は対象に取られない」は可）。設定シートの範囲では問題ありませんが、制約として意識しておく価値があります。

### 🟡 次に決めること

**5神すべてのカードをDSL化し終えました。カード側から出た宿題はすべて解消済みです。**

残るのは実装フェーズの課題が1つだけ:

**同じフェイズに複数の誘発が乗ったときの解決順**（例: `cycleStart` に生命のパッシブ生成・海の抱擁の判定・公開勝利条件のオープンが同時に乗る）。企画書の「同時にペナルティを受けた場合、先攻後攻どっちが先にスタックに乗るのか」と同じ問題系で、解決エンジンの設計で決めます。現時点の暫定案は「①先攻プレイヤーの誘発 → ②後攻プレイヤーの誘発、同一プレイヤー内はコントローラーが順序を選ぶ」です。
